# aisland — backlog

Open work for this project. Cross-cutting / multi-project initiatives live in the
workspace root `TASKS.md`. Completed items are not archived here — git history is the record.

- [ ] **From a wheel, aisland's own system tools are not provisioned** @low @infrastructure — `provision_system` reads `[tool.aisland.sys-dependencies]` from the discovered projects' `pyproject.toml`; aisland's own (process-compose for the services, swiftbar, colima, docker) sit in its `pyproject.toml`, which a wheel workspace does not discover and the wheel does not carry. Measured 2026-10-19: `aisland setup` in a workspace made by `aisland workspace init` printed `No system dependencies found.` Carry the list in the package (or read it from the distribution's metadata) and provision it in wheel mode; the README's "Another workspace" section says to install them by hand until then.
- [ ] **aisland is not on PyPI** @low @release — `https://pypi.org/pypi/aisland-manager/json` answers 404 (2026-10-19), so a wheel user builds it from this checkout (`python -m pip wheel --no-deps -w dist aisland`). Publishing it would make the README's install line `pip install aisland-manager` and let `aisland workspace init` print a real install command instead of `<the aisland wheel>`.
- [ ] **`aisland backups` has no scheduled sweep** @low @infrastructure — retention is applied by `aisland clean` and by `aisland backups prune`, both of which someone has to run. A machine that stops cleaning keeps its last backups forever. The pieces exist (`prune_store` is a one-line call); what is missing is a place to run it from — a launchd/systemd timer, or a hook in whatever runs `aisland doctor` on this machine.
- [ ] **`aisland source` for a project on a private INDEX:** the `pypi` kind assumes a public index. A project published to a private index would need the source entry to carry (or resolve) that index, which today only reaches uv via the generated root `uv.toml`. (A private *repository* is already covered — use `github`, whose URL comes from `.gitmodules`.) @low @infrastructure
- [ ] **Transitive Gearlux deps of a `pypi`-sourced project** are left to the published wheel's own metadata. That is correct for a leaf like loggair, but a published project that itself depends on an unpublished Gearlux package would fail to resolve — validate this at `aisland source set` time rather than at install time. @low @infrastructure
- [ ] **The scaffolded pre-install order and closure depend on which checkouts exist on the scaffolding machine** @low @maintenance — `services/jenkins.py` reads each dependency's `pyproject.toml` from disk (`_load_project_table`), and a detached submodule (empty directory) contributes no edges and no transitive dependencies, so the same workspace emits `loggair, confluid, liquifai` with checkouts present but alphabetical order with them detached. Only `Jenkinsfile` and `ci.yml` carry the list (`Jenkinsfile.local` installs nothing). Order is cosmetic under `--no-deps`, but it makes tracked-file content depend on per-machine disk state — derive the edges from a machine-independent source (or drop the sort).
- [ ] **`jenkins scaffold` measures the PARENT package's name for a project that ships inside another package** @low @maintenance — the generated `Jenkinsfile`/`Jenkinsfile.local`/`ci.yml` pass `--cov={pkg_name}` (`services/jenkins.py`), which for signals-bte, -wlan, -lte, -5gnr and -zigbee is `--cov=signals` and for raidar-ultralytics `--cov=raidar`. Measured on signals-bte: the report lists only that checkout's files — `signals/bte/*` plus the shim `signals/__init__.py`, counted 0 % because the parent's own `__init__.py` runs instead — so the percentage carries one unrunnable line and reads as though CI measured the parent. Derive the target from the project's `[tool.setuptools.packages.find] include` (the entry that is not the bare parent: `signals.bte`, `signals.wlan`, `signals.lte`, `signals.fivegnr`, `signals.zigbee`, `raidar.ultralytics`).
- [ ] **Bumping `CLEARML_SERVER_VERSION` needs a digest refresh, and nothing checks that** @low @maintenance — `services/clearml.py` pins the tag AND `COMPOSE_SHA256`; changing one without the other fails at `aisland clearml start` with a checksum mismatch, which is safe but late. A test cannot fetch (offline CI), so the options are a `--refresh-digest` flag that prints the new value or a doctor check behind a network guard.

- [ ] **Guard `tensorflow-metal` the way `opencv-python` is guarded** @low @maintenance — installing it BREAKS `import tensorflow` on this workspace: `tensorflow-metal` 1.2.0's `libmetal_plugin.dylib` needs `@rpath/_pywrap_tensorflow_internal.so`, and TF 2.21 ships that file with install name `bazel-out/darwin_arm64-opt/bin/tensorflow/python/lib__pywrap_tensorflow_12_shared_object.dylib`, so every TF run dies at import (measured with a real `pip install`, then uninstalled). Nothing declares it today, which is why nothing is broken — but "install the Metal plugin on a Mac" is the obvious next idea for anyone looking at the sweep's CPU rows. Same SHAPE as the `opencv-python` problem the root `AGENTS.md` documents, so the same two-part remedy fits: a never-true marker in the generated root `uv.toml` (`manager._ROOT_UV_BASE`, which today carries only `lightning`, `opencv-python` and `opencv-python-headless`) and an `aisland doctor` check (`doctor.py`, registered in `CHECKS`) that detects `site-packages/tensorflow-plugins/libmetal_plugin.dylib` beside a TF newer than 2.18 and prints the one-command fix. `jax-metal` needs no guard — it installs and registers cleanly, and fails loudly on the first computation (`unknown attribute code: 22 … StableHLO_v1.14.0`) rather than at import. The breakage is documented in `sonair/README.md`.
