# aisland — backlog

Open work for this project. Completed items are not archived here — git history is the record.

- [ ] **`aisland clean` does not sweep the tunnel's state** @low @maintenance — the tunnel keeps its CLI binary (~28 MB), log and account in `~/.aisland/tunnel` (per machine, so a `start` and a `status` run from different folders agree), which is outside the workspace state `clean` walks. Either teach `clean` that folder or leave it to `aisland tunnel stop` + a manual `rm`; nothing reclaims it today.
- [ ] **aisland is not on PyPI** @low @release — `https://pypi.org/pypi/aisland/json` answers 404 (2026-10-21), so a wheel user builds it from this checkout (`python -m pip wheel --no-deps -w dist aisland`). Publishing it makes the README's install line and the `pip install aisland` that `aisland workspace init` prints work.
- [ ] **`aisland backups` has no scheduled sweep** @low @infrastructure — retention is applied by `aisland clean` and by `aisland backups prune`, both of which someone has to run. A machine that stops cleaning keeps its last backups forever. The pieces exist (`prune_store` is a one-line call); what is missing is a place to run it from — a launchd/systemd timer, or a hook in whatever runs `aisland doctor` on this machine.
- [ ] **`aisland workspace configure source` for a project on a private INDEX:** the `pypi` kind assumes a public index. A project published to a private index would need the source entry to carry (or resolve) that index, which today only reaches uv via the generated root `uv.toml`. (A private *repository* is already covered — use `github`, whose URL comes from `.gitmodules`.) @low @infrastructure
- [ ] **Transitive workspace deps of a `pypi`-sourced project** are left to the published wheel's own metadata. That is correct for a leaf library, but a published project that itself depends on an unpublished workspace package would fail to resolve — validate this at `aisland workspace configure source set` time rather than at install time. @low @infrastructure
- [ ] **The scaffolded pre-install order and closure depend on which checkouts exist on the scaffolding machine** @low @maintenance — `ci/ci_scaffold.py` reads each dependency's `pyproject.toml` from disk (`_project_table`), and a detached submodule (empty directory) contributes no edges and no transitive dependencies, so the same workspace emits its dependencies in dependency order with checkouts present but in alphabetical order with them detached. Only `Jenkinsfile` and `ci.yml` carry the list (`Jenkinsfile.local` installs nothing). Order is cosmetic under `--no-deps`, but it makes tracked-file content depend on per-machine disk state — derive the edges from a machine-independent source (or drop the sort).
- [ ] **`jenkins scaffold` measures the PARENT package's name for a project that ships inside another package** @low @maintenance — the generated `Jenkinsfile`/`Jenkinsfile.local`/`ci.yml` pass `--cov={pkg_name}` (`ci_scaffold.py`), which for a child project (`vision-extra` shipping as `vision.extra`) is the parent's: `--cov=vision`. Measured on a child project: the report lists only that checkout's files — `vision/extra/*` plus the shim `vision/__init__.py`, counted 0 % because the parent's own `__init__.py` runs instead — so the percentage carries one unrunnable line and reads as though CI measured the parent. Derive the target from the project's `[tool.setuptools.packages.find] include` (the entry that is not the bare parent: `vision.extra`).
- [ ] **The `tracker` selection should offer a "local only" preset** @low @feature — the free self-hostable set (`mlflow`, `tensorboard`, `aim`) is the common choice on a laptop, and spelling all three every time invites a typo. A named preset would also give the docs one command to point at.
- [ ] **`docker-creds` doctor check ignores per-registry `credHelpers`** @low @maintenance — the check covers the measured skew (a dangling top-level `credsStore`), but a `credHelpers` map entry naming a missing helper produces the identical `exec: docker-credential-<x>: executable file not found` on pulls from that one registry. Same read, one more dict walk — extend `doctor.check_docker_credsstore` when it recurs.
- [ ] **Guard `tensorflow-metal` the way `opencv-python` is guarded** @low @maintenance — installing it BREAKS `import tensorflow` in a workspace with TensorFlow 2.21: `tensorflow-metal` 1.2.0's `libmetal_plugin.dylib` needs `@rpath/_pywrap_tensorflow_internal.so`, and TF 2.21 ships that file with install name `bazel-out/darwin_arm64-opt/bin/tensorflow/python/lib__pywrap_tensorflow_12_shared_object.dylib`, so every TF run dies at import (measured with a real `pip install`, then uninstalled). Nothing declares it today, which is why nothing is broken — but "install the Metal plugin on a Mac" is the obvious next idea for anyone looking at the sweep's CPU rows. Same SHAPE as the `opencv-python` problem (aisland rules → "Known Environment Skews"), so the same two-part remedy fits: a never-true marker in the generated root `uv.toml` (`setup.uv_config._ROOT_UV_BASE`, which today carries only `lightning`, `opencv-python` and `opencv-python-headless`) and an `aisland doctor` check (`doctor.py`, registered in `CHECKS`) that detects `site-packages/tensorflow-plugins/libmetal_plugin.dylib` beside a TF newer than 2.18 and prints the one-command fix. `jax-metal` needs no guard — it installs and registers cleanly, and fails loudly on the first computation (`unknown attribute code: 22 … StableHLO_v1.14.0`) rather than at import.
- [ ] `apply_selection` (`aisland workspace configure <selection> set`) still installs one project at a time (`Workspace.install_order`); route it through `workspace.projects.install_groups` so a cyclic pair is installed together there too.
- [ ] **The push `Jenkinsfile` has no stage time limit** @low @infrastructure — `Jenkinsfile.local` holds its long stages to `STAGE_LIMITS` and `ci.yml` to three times them; the push Jenkinsfile runs on another Jenkins whose speed is unmeasured. Add the `limited` wrapper there once it is, and drop `TestALongStageHasATimeLimit::test_the_push_jenkinsfile_carries_no_limit`. Check the `ci.yml` limits against a few GitHub runs' durations once aisland has some.
- [ ] **The local Jenkins does not run aisland's slow tests yet** @medium @infrastructure — aisland registered `slow` (2026-10-25: 7 tests `aisland tests report aisland` listed) and its `Jenkinsfile.local` gained the `SLOW_TESTS` parameter and Slow Tests stage, but the running Jenkins' orchestrator script was written at seeding and passes `SLOW_TESTS: slowTests()` only to the projects that had the marker then. Re-seed (`aisland jenkins init --local`, which stops Jenkins and prompts) or POST the new `config.xml` of `aisland.local` and the orchestrator (AGENTS.md → "Deploying a template change to a running Jenkins"); until then those tests run only on GitHub's slow leg and by hand (`pytest -m slow`).
- [ ] **Runnable examples for the docs pages that change a workspace** @low @docs — `examples/` covers the pages whose commands touch only a folder you name or nothing (`02_workspace_init`, `03_doctor`, `04_completion`, `05_notebooks_clean`, plus `01_tunnel_terminal`). The others — workspace setup, sources, selections, git, clean, wheels, services, CI, tests, editor, mcp, harness — have none: from a checkout aisland works on the workspace it is checked out in whatever the current folder, so `aisland setup`, `configure … set` or `clean` in an example would change the real workspace (and in CI, aisland's own checkout). An example for them needs aisland running from a wheel in a throwaway venv (the release smoke test's shape) inside a throwaway workspace; services, CI and the tunnel also need Docker, Jenkins or a remote machine.
