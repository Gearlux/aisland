# Aisland Mandates

## Current state

- **What it is:** the workspace's dev-infrastructure CLI (`aisland`, click): `manager.py` (workspace setup / provisioning), `supervisor.py` (process-compose delegation), and `services/` (`jenkins`, `mlflow`, `labelstudio`, `fiftyone`, `docker`, `swiftbar`); plus `aisland supervisor status|attach|down`.
- **Only supervisor-started services exist:** PID-file/`pgrep` detection is GONE — a service started outside the supervisor is INVISIBLE to it; the start-time port pre-flight naming the offending PID is the only signal.

## Mandates

- **The Workspace Root Marker Is `.gitmodules`, NOT `TASKS.md` (2026-07-27):** `manager.get_workspace_root()` resolves the SUPERPROJECT by walking up from `__file__` and preferring the one directory carrying **`.gitmodules`** (+ a `TASKS.md`); only when a checkout genuinely has no submodules does it fall back to the **OUTERMOST** `TASKS.md`, then the outermost `.git`. NEVER reinstate "first `TASKS.md` wins": the 2026-07-26 restructuring made backlogs PROJECT-OWNED, so every project dir has one and an innermost-match walk stops at a PROJECT — `aisland/TASKS.md` made the function return `<root>/aisland`, which silently (a) named the Jenkins orchestrator job `aisland.local` instead of `acme.local` (`get_workspace_name()` reads `git remote` at the resolved root), (b) set the global `WORKSPACE_ROOT` env to the aisland dir so every job's `customWorkspace` pointed at `<root>/aisland/<project>`, and (c) hid the workspace `.env` ("No workspace .env found; skipping injection"), leaving `DATA_ROOT` & friends out of every build. Nineteen call sites depend on this one function, so a marker change here is workspace-wide. The absolute fallback is `parents[2]` (`<root>/aisland/aisland/manager.py` -> `<root>`) — the old `parents[3]` was off by one and pointed ABOVE the workspace. Pins: `tests/test_workspace_root.py` (superproject wins over a nested `TASKS.md`; the pre-fix failure asserted explicitly; no-submodule + no-`TASKS.md` fallbacks; and a live check that the real checkout resolves to the `.gitmodules` dir).
- **Workspace-Relative Path Resolution:** All service binaries, data directories, and logs MUST resolve to the `aisland/` directory inside the current workspace root — discovered dynamically (e.g., by walking up from the invocation `cwd` to find `TASKS.md` or `.git`), never hardcoded to an absolute path like `~/source/aisland/`. The workspace root is derived from the `cwd` at invocation; the target directory is always `<workspace_root>/aisland/`, regardless of the subdirectory the `aisland` command is run from. Never pollute the workspace root itself with service state.
- **Supervisor-Based Lifecycle (supersedes the old PID-file mandate, 2026-07-06):** Process supervision (spawn, liveness, readiness, crash recovery, log capture, port discovery) is DELEGATED to process-compose via `aisland/supervisor.py`. Never spawn a service with a bare `Popen`, never track it with PID files or `pgrep` patterns, and never kill it with raw signals — register it in the generated desired-state document (`data/process-compose.yaml`, provenance-headed, gitignored) and `apply()`. Rules that keep the model consistent: (1) a stop is a `disabled: true` + apply, NEVER a bare `process stop` — otherwise the next config update resurrects the process; (2) startup success is judged by `supervisor.wait_for_outcome` (readiness probe passed / stable run / supervisor gave up), NOT by a momentary `is_running` — a crash-looping process flips `is_running` through its whole restart budget; (3) every HTTP service passes a `readiness={"port":…, "path":…}` probe to `start()`; (4) `start()` pre-flights the port (`supervisor.port_in_use`) so an orphan instance (e.g. pre-supervisor aisland) yields an actionable error instead of a crash-loop; (5) `project update` is a no-op on a byte-identical config, so a re-start after a failed run must `process start` explicitly (BaseService.start handles this); (6) NEVER write a secret literal into the document — credential env entries are `${VAR}` REFERENCES to workspace `.env` keys (e.g. Label Studio's `LABEL_STUDIO_PASSWORD=${LABELSTUDIO_PASSWORD}`), and `apply()` layers `supervisor.read_workspace_env()` over `os.environ` for the `project update` call because expansion is CLIENT-side at config load (the server loads `.env` once at startup and never re-reads it; an apply without the layering expands refs to empty strings and wipes the stored values — and a literal `$` in any document value would be expanded too, so don't put one in). The process-compose CLI surface these rules encode was verified empirically against v1.116.0.
- **macOS TCC Responsibility Lands On The Supervisor Binary (2026-07-09):** macOS attributes every supervised service's file access to the daemon tree's ROOT process — the process-compose server — NOT to the java/python actually doing the read. External-volume data (`DATA_ROOT=/Volumes/...`) therefore requires a Full Disk Access grant for the RESOLVED process-compose binary (System Settings → Privacy & Security → Full Disk Access), followed by a FULL supervisor restart (`aisland supervisor down && aisland start --background`) — granting java/python, or restarting only Jenkins, does NOT help. The denial surfaces as `PermissionError: [Errno 1] Operation not permitted` deep inside the service (canonical: huggingface_hub cache reads during a Jenkins notebook build) while the SAME command works interactively; the live-kernel-log signature is `kernel (Sandbox) System Policy: Python(NNN) deny(1) file-read-data /Volumes/...`. The grant pins to the VERSIONED Cellar path, so a process-compose upgrade silently orphans it — the formula is `brew pin`ned, and `supervisor._preflight_full_disk_access` warns at server start with the exact path to grant (skipping silently when the TCC db itself is unreadable — an inconclusive probe must never cry wolf). NEVER "fix" this class of failure by moving `DATA_ROOT` to the boot disk, editing project Jenkinsfiles, or weakening the volume's ownership settings; diagnose with a live `log stream` capture, not post-hoc file inspection (the file always looks fine afterwards). See README § "macOS: Full Disk Access for the supervisor".
- **Cross-Platform:** Process management MUST work on macOS, Linux, and Windows — via the supervisor: unix socket in `aisland/data/` on Unix, TCP (`AISLAND_SUPERVISOR_PORT`, default 9089) on Windows. The binary provisions via Homebrew (`f1bonacc1/tap/process-compose`, macOS) or the `USERSPACE_TOOLS` registry (Linux, arch-aware flat tarball).
- **Userspace Downloads Are Checksum-Verified:** Every `USERSPACE_TOOLS` entry MUST pin a per-architecture `sha256` (keyed by the same `{arch}` token used in the URL) taken from the upstream SHASUMS/checksums file. `_install_userspace_tool` verifies the tarball — freshly downloaded OR reused from cache — against the pinned digest BEFORE extraction; a mismatch aborts and deletes the tarball. When you bump a tool's `version`, refresh its digests in the SAME edit (`curl -sL <checksums-url>`), or the install will abort. An entry with no digest for the current arch installs UNVERIFIED with a loud warning — acceptable only as a transient state while pinning a brand-new tool, never for a shipped entry.
- **Recurring Venv Skew Becomes A Doctor Check, Not Just A Note (`aisland/doctor.py`, 2026-07-27):** When an environment-level breakage recurs — a shared-`.venv` package pair that goes inconsistent and fails FAR from its cause — documenting it in `AGENTS.md` is necessary but not sufficient: add a `check_*` function to `aisland/doctor.py` and register it in `CHECKS` so `aisland doctor` detects it in one line instead of a twenty-minute forensic session. Rules: (1) a check is cheap, read-only and SPECIFIC — it names a known skew and carries a copy-pasteable `remedy`, never a vague "something looks off" (`tests/test_doctor.py` asserts every failing result has a remedy); (2) any probe that IMPORTS a suspect library runs out-of-process via `_import_probe` — a broken native bundle can abort the interpreter, and a doctor that dies while diagnosing is worse than none; (3) `run_doctor()` returns an exit code (0 clean / 1 any failure) so a CI step can gate on it; (4) a check encodes an invariant enforced elsewhere and must cite WHERE — the opencv check mirrors `manager._ROOT_UV_BASE`'s `opencv-python ; sys_platform == 'never'` override (both distributions own `cv2/cv2.abi3.so` + `cv2/.dylibs/*`, so exactly one variant may be installed), and drifting from that source of truth is the failure mode to avoid. Do NOT turn the doctor into a generic linter of the venv; `pip check` already reports nominal-but-unsatisfiable pins (e.g. roboflow's opencv pin) that are NOT breakage.
- **Service Isolation:** Each service (Jenkins, MLflow) MUST have its own data directory and log file (`log_location` in the supervisor document). Never share state between services.
- **BaseService Contract:** All new services MUST extend `BaseService` and implement `start()`, `stop()`, `status()`, and `reset()`. Services own the domain logic (command line, env, readiness probe, config/.env publication); `BaseService` owns the supervisor delegation.
- **Job Seeding:** Jenkins `init` MUST auto-create multi-branch pipeline jobs for all workspace projects using config.xml templates.
- **Scaffolded Verify-Examples Runs Flat AND Directory Examples:** The Verify Examples step emitted by `aisland jenkins scaffold` (all three templates in `services/jenkins.py`: Jenkinsfile, Jenkinsfile.local, GH Actions ci.yml) executes `examples/*.py` AND `examples/*/run.py`. Directory examples opt into CI by shipping a `run.py`; network-dependent / install-only example apps (e.g. an installable demo CLI that needs a live API) opt out by not having one. Content pin: `tests/test_jenkins_scaffold.py::test_scaffold_emits_directory_example_runner`. Only confluid + liquifai were regenerated when this landed (2026-07-16); the sweep is now COMPLETE — all three files in all eighteen projects carry the loop, verified 2026-07-30 during a full `aisland jenkins scaffold --force`.
- **The Regenerate Header Must Be A RUNNABLE Command (2026-07-30):** all three templates emit `To regenerate: aisland jenkins scaffold <name> --force`. It said `--project <name>` for months, which fails with `Error: No such option: --project` — the project is a click ARGUMENT, not an option — so the only instruction a generated file carries was one that could not be followed (hit while regenerating recordstream after its framework declaration changed; the same wrong form had been copied into the workspace `AGENTS.md` provenance example, fixed with it). The pin PARSES the emitted line with the real `jenkins_scaffold` command object (`make_context`) instead of string-matching, so it tracks the CLI's signature rather than restating it, and it does reject the old form (`NoSuchOption`, checked). When a generator's CLI signature changes, its header changes in the SAME edit — then re-scaffold, because every previously-generated file still carries the old line. Pins: `tests/test_jenkins_scaffold.py::test_the_regenerate_header_is_a_command_the_cli_accepts`.
- **Shell Completion Has THREE Families, And The COMMAND Owns Them — `aisland completion install` (2026-07-31, supersedes "Keep All Three In `setup.sh` §5"):** The workspace has three kinds of CLI and each needs its own mechanism, all written into the ONE generated `.project.bashrc.completion`: (a) **liquifai apps** (the `liquifai.apps` entry-point group — `recordstream`, `sonair`, `annotaide`, `raidar`, …) via `liquifai.completion.install_for_apps`, called IN-PROCESS rather than through the `liquifai-install-completions` console script, so a PATH miss cannot silently skip the whole family; (b) **click apps** (`aisland` itself) via click's `_<PROG>_COMPLETE=<shell>_source` protocol, guarded on `BASH_VERSINFO >= 4.4` for bash because click REFUSES to emit for older bash and macOS `/bin/bash` is 3.2; (c) **argparse apps** (`streamstudio`) via `argcomplete` (`register-python-argcomplete`), which requires the app to call `argcomplete.autocomplete(parser)` before `parse_args` AND to DECLARE `argcomplete` as its own dependency (never lean on the transitive copy that arrives via fiftyone). A new CLI that is none of these three silently gets NO completion — that was the `aisland`/`streamstudio` gap. **The ~70 lines of inline shell in `setup.sh` §5/5a/5b were REPLACED by `aisland/aisland/completion.py` + `aisland completion install` (setup.sh now calls it in one line, pinned by `tests/test_completion.py::test_setup_sh_delegates_instead_of_reimplementing`).** The reason is a measured failure, not tidiness: a completion fix could only reach a machine via a FULL provisioning run (venv + `aisland setup` + git config), which nobody does to refresh a tab-completion — so this workspace's own generated file sat at its 2026-07-02 content while §5b, added 2026-07-27, never ran, and `aisland <TAB>` did nothing for a month with no signal anywhere. Do NOT move this logic back into shell or duplicate it there. **`--target-rc` is part of the contract:** the default is the workspace fragment `project.bashrc` sources, and a user may point it at `~/.bashrc` / `project.bashrc` instead; an existing rc is APPENDED to (marked blocks only), never overwritten. **Pruning is mandatory, not optional:** `liquifai/completion/install.py::_replace_block` MERGES by marker and leaves blocks it did not write untouched, so a renamed/removed CLI keeps a dead block forever (the `fluxstudio` -> `streamstudio` rename left exactly that; `marainer` was pruned on the first real run, its CLI having been retired). Two safety rails, both load-bearing: the pruner STANDS DOWN when discovery found no liquifai app at all (that means discovery is broken, not that every app was uninstalled — pruning on that signal empties the file), and program lookup is VENV-FIRST (`sys.prefix/bin`, then `PATH`) so running from an unactivated venv cannot make every app look missing. Rationale: `docs/architecture.md`. Pins: `tests/test_completion.py`.
- **The Workspace Pins A Python VERSION, With An Upper Bound (`setup.sh` `WORKSPACE_PYTHON`, 2026-07-31):** the venv is built on the version `WORKSPACE_PYTHON` names (currently **3.13**), and an EXISTING venv is compared against it EXACTLY — not against a `>=3.12` range — because the pin has a ceiling as well as a floor, so a NEWER interpreter is just as wrong as an older one and a range check would silently keep it. The ceiling is about WHEELS, not language features: **TensorFlow 2.21 publishes cp310-cp313 only**, so on a 3.14 venv `uv pip install tensorflow` fails outright (*"we only found wheels ... cp310, cp311, cp312, cp313"*) and the framework is uninstallable no matter what `frameworks.toml` selects — which is exactly how a workspace ends up believing a framework was omitted for size. Raise the pin only when every framework this workspace installs ships wheels for the next version; check TensorFlow first, it lags most. Two further fixes landed with it, both real breakages hit while migrating: **`uv venv` does NOT seed pip** (unlike `python -m venv`), so the bootstrap died at `pip: command not found` and now seeds via `ensurepip`; and **`setup.sh` must call `aisland setup -y`**, because the bare form is INTERACTIVE and re-asks about every optional submodule — with no TTY (a background shell, CI, an agent) it blocks forever on `Activate 'raidar-ultralytics'? [y/N]:`. `-y` reuses the decisions already in `.git/config`; a genuinely NEW optional module still prompts, which is the deliberate conscious-opt-in behaviour. **One trap to know before running `aisland setup` on a machine mid-feature:** it runs `source apply`, which enforces the committed `sources.toml` ref — so a project whose checkout you have moved to `dev/main` for unmerged work gets switched back to `main`. That broke sonair outright during this migration (confluid's `framework=` axis and its 0.3.0 version live only on `dev/main`; on `main` it is 0.2.0 without the axis, so every `@configurable(framework=...)` raises `TypeError` and sonair will not even install). Nothing is lost — `git switch dev/main` restores it — but the editable METADATA must be refreshed too (`uv pip install -e ./confluid`), since a branch switch changes the source while the recorded version stays stale and the resolver keeps failing the floor.
- **Generated Workspace Files Are Portable + Gitignored:** Files `aisland setup` writes to the workspace root (`pyrightconfig.json` via `manager._write_pyrightconfig`, the `project.bashrc` symlink, `.project.bashrc.completion`, `.gemini/settings.json` via `manager._write_gemini_settings`, and the root `uv.toml` via `manager._write_root_uv_toml`) are generated artifacts: gitignore them and regenerate on every setup so the tree never goes dirty and the output always tracks the live project set (discovered via `get_install_order` / `discover_projects` / `_discover_mcp_servers`, not a hand-maintained list). Prefer workspace-relative paths (e.g. pyrightconfig's `venvPath: "."`) — never bake in an absolute like `/Users/<name>/acme`. **Per-project editor config is generated too:** `_write_pyrightconfig` also drops a `pyrightconfig.json` into EVERY discovered project dir (`venvPath` walking back to the shared workspace `.venv`, sibling projects on `extraPaths` — for opening one project as its own editor root) and appends `/pyrightconfig.json` to that project's `.gitignore` when missing (`_ensure_gitignore_line`, append-only/idempotent like `_sync_mypy_path`). NEVER commit editor extraPaths again — the retired committed `.vscode/settings.json` copies drifted (they still named pre-rename projects) and leaked workspace sibling paths to external consumers; pyright ignores `python.analysis.extraPaths` from `settings.json` whenever a `pyrightconfig.json` is present, so stale local settings are neutralized. **Exception:** `.gemini/settings.json` MUST use ABSOLUTE venv paths because the MCP client (Gemini CLI) launches each server as a subprocess from an arbitrary cwd; that machine-specific absolute is precisely why the file is gitignored + regenerated per machine rather than committed. Don't "portability-fix" it to relative paths — that breaks the launcher.
- **Root `mypy.ini` Is Committed — Setup Only Appends To `mypy_path`:** Unlike the generated files above, the workspace-root `mypy.ini` is committed, hand-maintained policy (the per-module `[mypy-*]` sections). `aisland setup` (`manager._sync_mypy_path`) keeps exactly one line complete: `mypy_path` gains any discovered project that is missing, APPEND-ONLY — never remove entries (inactive submodules stay listed; mypy ignores path entries that don't exist on this machine, which keeps the committed file identical across machines) and never touch hand-added nested entries (`confluid/confluid`, `aisland/aisland`). Do not convert mypy.ini into a generated artifact — gates (Jenkins, fresh clones) must be able to run mypy before any setup has executed.
- **Root `uv.toml` Is Generated From The Activated Set (Never Committed With A Private Index):** The root `uv.toml` is built by `manager._write_root_uv_toml` = a workspace base (`_ROOT_UV_BASE` — the `override-dependencies` policy: the unified `lightning` and the GUI `opencv-python` dropped workspace-wide via uv's never-true `sys_platform == 'never'` marker, plus `opencv-python-headless>=4.12,<5`; rationale in the `_ROOT_UV_BASE` comment and the root `AGENTS.md`, pinned by `tests/test_uv_activation.py::_OVERRIDE`) **merged** with each ACTIVATED project's own `uv.toml` (union list keys like `extra-index-url` with dedup, last-wins scalars; hand-emitted via `_emit_uv_toml` with an AUTO-GENERATED provenance header). A private index (Company Artifactory) lives in the owning project's `uv.toml` (e.g. `vendorcli/uv.toml`) and reaches the root file ONLY when that project is activated. This is why the root `uv.toml` MUST stay gitignored and regenerated per machine: a non-corporate machine that does not activate vendorcli/bridge never gets the (unreachable) index, so `uv pip install` from the root never tries to contact it. NEVER commit a root `uv.toml` carrying a private `extra-index-url`, and NEVER move a private index back into the root base — it belongs in the project's `uv.toml`.
- **Project Sources Are Two-Layered, And Only The COMMITTED Layer May Reach A Committed File (`aisland/sources.py`, 2026-07-28):** `aisland source` decides where each workspace project's package comes from — THREE kinds (`SourceKind`, 2026-07-28): `local` (checked out on a `ref`, installed editable), `github` (submodule deinit'd, directory EMPTY, installed from the remote at `ref`) and `pypi` (deinit'd, published wheel). `local`/`github` both carry a `ref` (`REF_KINDS`) and differ ONLY in whether a working tree survives; `github`/`pypi` both empty the directory (`DETACHED_KINDS`, exposed as `ProjectSource.detached` — derive from these tuples, never re-test kinds by hand). The naming is deliberate and must not be "simplified" back to `git`/`github`: the two commands are one word apart and two of the three run `git submodule deinit`, so a three-character difference between keeping and DELETING a checkout was rejected. A project with no entry is *unmanaged* and keeps the historical behaviour exactly — `DEFAULT_REF = "main"` exists so an unmanaged project and an explicit `local:main` produce byte-identical build files. Configuration is layered like submodule activation: the COMMITTED `<workspace>/sources.toml` (shared) plus a per-machine `git config --local aisland.source.<project>` override (never committed). **The split of what each layer drives is the invariant, not a detail:** the committed layer alone drives the `*.code-workspace` `folders` list (via `sources.sync_code_workspace`) and the ONE bit the runner-side CI files read; the EFFECTIVE source (override, else committed) drives only the submodule checkout and the shared `.venv`. NEVER let an override reach a tracked artifact, and NEVER read the effective source inside the scaffolder. **CI reads the published/not bit and NOTHING else — in particular it IGNORES the `ref` (2026-07-28):** a runner always clones `DEFAULT_REF`, and a `pypi`-sourced dep is dropped from the pre-install loop so `.[dev]` resolves it from the index. A `ref` is a DEVELOPMENT pin; letting it reach a tracked file would publish one developer's choice to every consumer's CI *and* rewrite seventeen projects' committed files on every switch. `_publishedness_changed` enforces the corollary: `aisland source set --ref`, and any `local` <-> `github` switch, regenerate NOTHING; only crossing the `pypi` boundary re-scaffolds. **`Jenkinsfile.local` reads NO source configuration at all** — every internal dep gets the IDENTICAL `[ -f "$WORKSPACE_ROOT/<dep>/pyproject.toml" ]` guard falling back to `git@main`, making that file a function of the dependency LIST alone, which no `aisland source` change of any kind can rewrite. The guard is not defensive polish: it asks at BUILD time exactly the question the config answers ("does this machine have a checkout?"), which is also what makes a per-machine override — by design invisible to tracked files — work instead of failing on an empty directory. Do NOT reintroduce per-kind branching there; the uniformity IS the property. **The predicate MUST test the FILE, never `-d` on the directory (2026-07-29):** `git submodule deinit` empties the working tree but LEAVES THE DIRECTORY, so `[ -d ]` is true for every detached dep — the editable branch then fires against an empty directory and every consumer's local pipeline dies at the Initialize stage with ``error: <dir> does not appear to be a Python project, as neither `pyproject.toml` nor `setup.py` are present``, with the git fallback unreachable. `pyproject.toml` is the file `uv pip install -e` actually consumes, so testing it asks the real question. Pinned by `tests/test_sources.py::TestScaffoldHonoursSources::test_guard_takes_the_git_branch_on_a_deinitd_directory`, which runs the emitted shell against a real empty dir rather than asserting on the emitted string. Its one accepted cost: a `pypi`-sourced dep is built from `main` in the local pipeline rather than from the released wheel, so that file alone diverges from the venv and from `ci.yml` — deliberate, because the local pipeline exists to catch breakage BEFORE a release. Availability on PyPI is decided ONCE, at `aisland source set … pypi` time (the provenance probe); scaffolding MUST NOT re-probe the index, or committed file content would depend on network reachability and an offline scaffold would flip every project to git URLs. Three more rules the implementation encodes, each protecting against a failure that would otherwise land AFTER the directory was already emptied: (1) a `pypi` switch resolves the distribution name from `pyproject.toml` BEFORE deinit (afterwards there is nothing left to read — which is why `distribution` is persisted into the registry); (2) each detaching kind is validated BEFORE the deinit and an inconclusive probe NEVER rejects — `_pypi_provenance` requires the published metadata to point at `github.com/Gearlux/…`, NOT merely that the name resolves (PyPI names are global, so a bare existence check would install a stranger's package into the shared venv when a workspace name is taken — `purifai` is exactly such a name), and `_remote_ref_exists` requires the `github` ref to resolve via one `git ls-remote` (non-zero exit = unreachable = inconclusive; exit 0 with empty output = the remote answered and has no such ref); an unreachable index or remote warns and continues, never a false rejection that would block an offline machine; (3) neither `git switch` nor `git submodule deinit` is ever forced — a dirty submodule refuses, is reported **with the remedy matching the ACTUAL blocker** (`_deinit_remedy`, 2026-07-28: git words BOTH refusal causes as "contains local modifications", but their fixes live in different repositories — a dirty work tree is fixed IN the submodule, while a **stale gitlink** (the checkout sitting at a commit other than the one the superproject records, the common case right after committing in a submodule without bumping the pointer) is fixed by committing the pointer in the WORKSPACE repo; the message probed nothing and always said "commit or stash the changes in `<sub>`", sending the operator hunting through a spotless tree — so probe each, report only what is true, and stay generic when a probe cannot answer), the venv is left untouched, AND `set_project_source` ROLLS THE CONFIGURATION BACK, because a registry claiming a state the working tree does not have would be re-attempted by every subsequent `aisland setup`. `manager.reconcile_submodules` folds `sources.detached_projects()` into its active set so the activation machinery cannot re-init a directory the source says is empty. **A DETACHED project must still be discoverable by the scaffolder:** `jenkins.discover_gearlux_projects` reads each submodule's `pyproject.toml` for its distribution name, which an emptied directory no longer has — so it ALSO seeds from the committed registry's `distribution` field (that field exists for exactly this reason). Dropping that fallback is silent and severe for `github`: the dep vanishes from the internal set, the git-URL pin disappears, and CI resolves the PyPI RELEASE instead of the requested ref (or fails outright for an unpublished project) — found by running a real scaffold, not by a unit test, and now pinned by `tests/test_sources.py::TestScaffoldHonoursSources::test_github_dep_survives_its_own_empty_directory`. The `github` remote URL comes from `.gitmodules` (`sources.remote_url`), never a hardcoded `github.com/Gearlux/<name>`, so the non-GitHub submodules work too; `pip_vcs_url` rewrites an scp-style `git@host:org/repo` to `git+ssh://git@host/org/repo` because pip cannot parse the scp form. Pins: `tests/test_sources.py` (layering, the byte-lossless `folders` round trip, the guard's emission AND its behaviour on a real empty directory, the argv sequence per kind, the reconcile interaction).
- **Selection Is Axis-Generic — `aisland/selection.py` Owns The Mechanism, `frameworks.py` Is A FACADE (2026-08-01):** the declare/select machinery moved to `aisland/selection.py` and is parameterized by an `Axis` (`name`/`plural` -> `<plural>.toml`, `aisland.<plural>` git key, `[tool.aisland] <plural>` table). TWO axes exist and are **SIBLINGS, never merged**: `FRAMEWORKS` (what a machine TRAINS WITH) and `TRACKERS` (where results GO — `marainer[mlflow]`/`[aim]`/`[tensorboard]`/`[wandb]`). Folding the backends into `frameworks` would install a tracking client because someone picked a training engine; that is why marainer's `pyproject.toml` declares them as a separate `trackers = [...]` key, and why `aisland tracker` is its own command group rather than more names under `framework`. **`aisland/frameworks.py` is now a thin facade** keeping every `*_frameworks` name bound to the framework axis, so `manager.py`, `services/jenkins.py`, `cli.py` and `tests/test_frameworks.py` were untouched by the move — do NOT "clean it up" by rewriting those call sites; the facade is what made a 200-line mechanism shareable without a ripple. A module named `frameworks` owning the tracker axis would describe its first consumer rather than its role (the same correction as marainer's `lightning.metrics` -> `torch.metrics`). **Three rules the generic code encodes:** (1) `all_extras()` spans BOTH axes and is what `setup` and `apply_selection` install — a target naming only the axis being changed describes a package the operator never asked for, so changing trackers must not drop the framework extras; (2) the CI scaffolder loops `AXES` and reads `read_committed` ONLY, never `effective` — a per-machine override reaching a tracked build file is the failure the whole two-layer split exists to prevent, and for trackers it is worse than for frameworks because a runner that stops installing mlflow makes those tests **SKIP rather than fail** (`pytest.importorskip`), i.e. a green CI that checks nothing; (3) a project declaring neither axis emits the historical `.[dev]` unchanged. Pins: `tests/test_selection.py` (axis independence, `all_extras` across both, the header naming the right command), `tests/test_frameworks.py::TestScaffolderUsesThisModule` (the committed-only binding + that the scaffolder covers every axis).
- **A Service MUST NOT Install Its Own Backend (`services/mlflow.py`, `services/aim.py`, 2026-08-01):** `MLflowService.setup()` used to `pip install mlflow` when the import was missing. That contradicts the selection layer it depends on: which backends a machine has is decided by `aisland tracker` and recorded in `trackers.toml` / `.git/config`, so an ad-hoc install leaves the venv holding something no selection asked for — and gone again after the next `aisland setup`. Both now raise a `ClickException` naming `aisland tracker set <name>`. A future ClearML service does the same: **assert and point at the selection command, never install**. (`FiftyOneService.setup` still lazy-installs; it is not on a selection axis, so it is out of scope rather than an exception — put it on one before "fixing" it.)
- **`aisland clearml` VENDORS NOTHING — Pinned Upstream Compose + A GENERATED Override (`services/clearml.py`, 2026-08-01):** the ClearML server is seven containers, and upstream publishes the compose that wires them; this service fetches that file at a **release tag** (`CLEARML_SERVER_VERSION`, currently `v2.4.0`) and verifies it against `COMPOSE_SHA256` before caching — the `USERSPACE_TOOLS` checksum rule applied to a config artifact, and the reason the pin must be a TAG and never `master` (a digest pinned to a moving ref breaks on upstream's next commit; `tests/test_clearml_service.py` asserts it). **Upstream hardcodes `/opt/clearml/...` host paths**, which would put service state outside the workspace and need root — so aisland layers an override that remaps every bind mount into `aisland/data/clearml/state`. Three facts hold it together, all MEASURED rather than assumed: (1) **compose merges a service's `volumes` by container TARGET** — an override naming the same target REPLACES the entry rather than adding a second (verified with `docker compose config` before any of this was written; had it appended, the whole design was wrong); (2) the override is **GENERATED from the upstream file**, never hand-listed, so bumping the version cannot leave a stale path behind and a mount upstream adds later is remapped automatically; (3) upstream comes FIRST in the `-f` order, because compose applies later files over earlier ones. **Docker owns the lifecycle, not the supervisor** — `launch`/`stop`/`status` shell out to `docker compose`, and `info()` deliberately does NOT call `super().info()` because the base prints a "Supervisor: process-compose" line that would send an operator to the wrong tool. **Verified end to end 2026-08-01:** all eight containers up, web `HTTP 200`, `auth.login`… no — `debug.ping` returned `result_code: 200`, 209 MB of state under `aisland/data/clearml/state` and **`/opt/clearml` absent from the host**, then `stop` removed the containers with the state intact. **Credentials are minted HEADLESSLY, and the mechanism is not the obvious one (2026-08-01):** a fresh stack reports `login.supported_modes` -> `basic.enabled: false`, so nothing can log in until a fixed user exists. Enabling one through `CLEARML__apiserver__auth__fixed_users__users__0__username=…` environment variables **does not work** — that override cannot express a LIST OF OBJECTS, and the server then dies on EVERY login with `FixedUser() argument after ** must be a mapping, not str` (measured; the stack looks healthy and only auth is broken). The working mechanism is ClearML's documented one: an `apiserver.conf` written into the mounted config directory (`state/config/`, which the override already binds to `/opt/clearml/config`), **before** `up`, because the apiserver reads that directory at startup. `launch()` then waits for `debug.ping`, calls `auth.login` + `auth.create_credentials`, and records `CLEARML_API_ACCESS_KEY`/`SECRET_KEY` in the workspace `.env`. The password IS a literal in that file — the server has to read it — so it is 0600 and lives in gitignored machine-local state beside the `.env` that already holds it; an existing login is REUSED rather than regenerated, since a fresh password would not match the server that already has the old one. Minting never raises: a stack that is otherwise up must not fail over a tracking convenience. **Verified end to end 2026-08-01:** a `ClearMLTracker` against the live server produced a `completed` task carrying the hyperparameters, the flattened `datasets` section, the manifest in the Configuration tab, and `manifest.yaml`/`manifest.json`/the log as artifacts. One interop constraint found while doing it: ClearML rejects a task name shorter than three characters (`Data validation error: name=String value is too short`).
- **`aisland aim` Serves A REPOSITORY, And The Path Is The Contract (`services/aim.py`, 2026-08-01):** Aim has no server — `aim up --repo <dir>` serves a directory — so the service is only useful if it serves the SAME directory the tracker writes to. `launch()` therefore publishes the path to the workspace `.env` as **`AIM_REPO`** (`_publish_repo`, replacing a stale entry in place and leaving neighbouring keys untouched), and a run config points its tracker at `$AIM_REPO`. Do NOT drop that publication as redundant: without it a run writes to one repository and the UI serves another, and the symptom is "my runs aren't showing up" with nothing in any log. Two further details, both measured: `--yes` is REQUIRED on the command line (Aim prompts to initialise a repository it has not seen, and a supervised process has no one to answer, so it hangs instead of starting), and the binary is resolved **venv-first** (`sys.prefix/bin/aim`, then PATH) so an unactivated shell cannot serve a different Aim. A freshly-finished run missing from the UI is Aim's INDEX, not a lost write — `aim up` indexes at startup, so a restart shows it (see marainer's `aim_backend` docstring). Pins: `tests/test_aim_service.py`.
- **Framework Selection Is Two-Layered Like Sources; Only The COMMITTED Layer May Reach CI (`aisland/frameworks.py` -> now `aisland/selection.py`, 2026-07-30):** workspace packages keep their core framework-free and put each ML framework behind an EXTRA (`recordstream[torch]`, `sonair[lightning]`/`[keras]`), so something must decide WHICH — before this module `aisland setup` installed `<project>[dev]` and nothing else, which after the extras split produced a sonair with no backend at all. TWO halves, deliberately separate: a project **declares** which of ITS extras are frameworks in its own `pyproject.toml` (`[tool.aisland] frameworks = ["lightning", "keras"]`), and the workspace **selects** framework NAMES; each project installs what it declares ∩ what is selected (`extras_for`, ordered by the DECLARATION so the emitted target is stable however the names were typed). Declaration is required rather than guessed because extras are a mixed bag — `dev`/`http`/`viz`/`notebook`/`all` sit in the same table as `torch`/`keras`, and a name match would install a docs extra on a machine that asked for a training engine. **Declare only IMPLEMENTED frameworks:** sonair keeps `jax`/`mlx`/`huggingface` extras so its CLI templates can print a real install command, but declaring them would install three frameworks nothing can run. Declaring is the MENU, not the install: sonair added `tensorflow` and `fastai` to its declaration on 2026-07-30 when both backends became real, and the committed SELECTION still omits `tensorflow` — so nothing new installs until someone runs `aisland framework set … tensorflow`. That split is what lets a project advertise a working backend whose install cost (TensorFlow is a large download) stays a deliberate opt-in. It is NOT a dependency conflict — the long-standing "TF forces protobuf across mlflow/tensorboard/wandb" claim was measured wrong and corrected 2026-07-30; see sonair's `AGENTS.md`. A project declaring NONE is inert — it installs exactly as before, which is what keeps this change invisible for the fifteen-odd projects that ship no framework extra. The names line up across projects ON PURPOSE (`keras` is `keras` everywhere) so ONE selection drives everything with no per-project mapping table. **Layering mirrors `aisland/sources.py` exactly, and the same invariant is the point:** the COMMITTED `frameworks.toml` is the shared default AND the only layer `jenkins.scaffold_pipelines` reads (via `ci_extras`), while the per-machine `git config --local aisland.frameworks` drives ONLY this machine's `.venv`. Never let an override reach a tracked build file — one developer narrowing to torch locally would silently stop every runner from testing the Keras backend, a failure that shows up as a green CI that no longer checks anything. **`None` (unset) is NOT `[]` (chose nothing):** setup PROMPTS for the former and honours the latter silently; `--non-interactive` with nothing recorded selects everything rather than hanging or producing a workspace that cannot train, and an explicit `--framework` flag is RECORDED so it is a one-time flag. **`apply_frameworks` MUST iterate `get_install_order`, never `discover_projects`** — a consumer's extra can name a sibling's (`sonair[keras]` requires `marainer[keras]>=0.1.0`), so installing the consumer first resolves against the sibling's ALREADY-INSTALLED metadata and uv warns `does not have an extra named 'keras'` while quietly installing without it (observed on the first real run). Accepted cost: uv does not UNINSTALL a deselected extra — guessing which packages 'belonged' to one is unsound, so a stale wheel costs disk, not correctness; recreate the venv for a clean set. Verified 2026-07-30 that the full framework set co-resolves (torch 2.13 + tensorflow 2.20 + keras 3.15 + pytorch-lightning 2.6.5 on one numpy), so "CI installs everything" is a measured option rather than a hope. **ONLY projects that OFFER a choice are declarable, and the four that REQUIRE torch are deliberately NOT (decided 2026-07-30 by reading each, not by counting imports):** `signals` (`schema.py`, "THE builder for the record model", enforces `torch.complex64` IQ — torch IS the canonical representation), `deltaid` ("a standard PyTorch-Lightning semantic segmenter" per its own docstring), `raidar` + `raidar-ultralytics` (torch/ultralytics detection trainers whose `__init__.py` imports them eagerly). Moving their deps behind a `[torch]` extra was considered and REJECTED — `pip install raidar` would yield a package whose `__init__` raises `ImportError`, dishonest packaging for a project that genuinely needs torch. **Do NOT "finish the job" by declaring them**; the accepted consequence is that `aisland framework set keras` on a FULL workspace still installs torch, because this command narrows MULTI-BACKEND projects and never promised a framework-free venv. `torpaido` was NOT such a case and was fixed instead: it declared `torch` while referencing it zero times across its three modules, so the dependency was dropped outright. If a genuinely torch-free venv is ever wanted, the path is a new "skip this project unless its framework is selected" mechanism, not a fake extra. Rationale: `docs/architecture.md`. Pins: `tests/test_frameworks.py` (the layers, the unset/empty distinction, the setup precedence, and that the scaffolder reads the committed layer ONLY).
- **The `*.code-workspace` `folders` List Is Edited LINE-WISE, Never Reparsed (2026-07-28):** the workspace file is **JSONC** — `settings` carries `//` comments and trailing commas, so `json.load` fails on it outright (line 121 of the real `acme.code-workspace`). `sources.sync_code_workspace` therefore bracket-scans only the `folders` span and edits it as lines, and a disabled project is **commented out in place** rather than deleted. That is not cosmetic: it keeps the entry's position in a list that is dependency-ordered rather than alphabetical, and makes comment→uncomment byte-for-byte lossless, so flipping a project to `pypi` and back leaves `git diff` clean (asserted against the real file's structure in `tests/test_sources.py::TestSyncCodeWorkspace::test_round_trip_is_byte_identical`). NEVER "simplify" this to a JSON round trip — it would reformat a hand-maintained committed file and drop every comment in it. Entries for projects NOT named in `sources.toml` (`vendorcli`, `signals-bridge`, `raidar-ultralytics`) are left untouched; they are governed by the activation mechanism, not this one.
- **Submodule Activation Is Per-Machine + Prompt-Driven:** `aisland setup` resolves *optional* submodules (`manager._project_is_optional` → ships its own `uv.toml` OR is `active = false` in `.gitmodules`; ordinary projects auto-activate and are never prompted) and records the answer per-machine in `.git/config` (`submodule.<name>.active`, via `_set_local_submodule_active`) — NEVER in committed `.gitmodules` (that file's `active` flag is the shared default only). Semantics (`_resolve_submodule_activation`): a decided module (a value already in `.git/config`) is honored silently; an undecided/NEW optional module is **prompted even under `--non-interactive/-y`** (a machine must consciously opt into a private/corporate project before it tries to use its index or clone its remote); `--activate <name>` / `--deactivate <name>` set the decision without prompting. `reconcile_submodules` then aligns the working tree with `committed_active if local is None else local`, so a per-machine deactivate deinits a committed-active submodule. Keep the deinit protective (no `-f`) unless the user asks otherwise.
