# Aisland Mandates

## Current state

- **What it is:** the workspace's dev-infrastructure CLI (`aisland`, click): `manager.py` (workspace setup / provisioning), `config.py` (the one committed `config.toml`, read/written by `sources.py` + `selection.py`), `supervisor.py` (process-compose delegation), `clean.py` (`aisland clean <project>` — git-ignored content moved to a dated backup), and `services/` (`jenkins`, `mlflow`, `labelstudio`, `fiftyone`, `aim`, `swiftbar` on the supervisor; `docker` (Colima) and the containerised `clearml`, `iqengine` on Docker); plus `aisland supervisor status|attach|down`.
- **Only supervisor-started services exist:** PID-file/`pgrep` detection is GONE — a service started outside the supervisor is INVISIBLE to it; the start-time port pre-flight naming the offending PID is the only signal.

## Mandates

- **The Workspace Root Marker Is `.gitmodules`, NOT `TASKS.md` (2026-07-27):** `manager.get_workspace_root()` resolves the SUPERPROJECT by walking up from `__file__` and preferring the one directory carrying **`.gitmodules`** (+ a `TASKS.md`); only when a checkout genuinely has no submodules does it fall back to the **OUTERMOST** `TASKS.md`, then the outermost `.git`. NEVER reinstate "first `TASKS.md` wins": the 2026-07-26 restructuring made backlogs PROJECT-OWNED, so every project dir has one and an innermost-match walk stops at a PROJECT — `aisland/TASKS.md` made the function return `<root>/aisland`, which silently (a) named the Jenkins orchestrator job `aisland.local` instead of `acme.local` (`get_workspace_name()` reads `git remote` at the resolved root), (b) set the global `WORKSPACE_ROOT` env to the aisland dir so every job's `customWorkspace` pointed at `<root>/aisland/<project>`, and (c) hid the workspace `.env` ("No workspace .env found; skipping injection"), leaving `DATA_ROOT` & friends out of every build. Nineteen call sites depend on this one function, so a marker change here is workspace-wide. The absolute fallback is `parents[2]` (`<root>/aisland/aisland/manager.py` -> `<root>`) — the old `parents[3]` was off by one and pointed ABOVE the workspace. Pins: `tests/test_workspace_root.py` (superproject wins over a nested `TASKS.md`; the pre-fix failure asserted explicitly; no-submodule + no-`TASKS.md` fallbacks; and a live check that the real checkout resolves to the `.gitmodules` dir).
- **Workspace-Relative Path Resolution:** All service binaries, data directories, and logs MUST resolve to the `aisland/` directory inside the current workspace root — discovered dynamically (e.g., by walking up from the invocation `cwd` to find `TASKS.md` or `.git`), never hardcoded to an absolute path like `~/source/aisland/`. The workspace root is derived from the `cwd` at invocation; the target directory is always `<workspace_root>/aisland/`, regardless of the subdirectory the `aisland` command is run from. Never pollute the workspace root itself with service state.
- **Supervisor-Based Lifecycle (supersedes the old PID-file mandate, 2026-07-06):** Process supervision (spawn, liveness, readiness, crash recovery, log capture, port discovery) is DELEGATED to process-compose via `aisland/supervisor.py`. Never spawn a service with a bare `Popen`, never track it with PID files or `pgrep` patterns, and never kill it with raw signals — register it in the generated desired-state document (`data/process-compose.yaml`, provenance-headed, gitignored) and `apply()`. Rules that keep the model consistent: (1) a stop is a `disabled: true` + apply, NEVER a bare `process stop` — otherwise the next config update resurrects the process; (2) startup success is judged by `supervisor.wait_for_outcome` (readiness probe passed / stable run / supervisor gave up), NOT by a momentary `is_running` — a crash-looping process flips `is_running` through its whole restart budget; (3) every HTTP service passes a `readiness={"port":…, "path":…}` probe to `start()`; (4) `start()` pre-flights the port (`supervisor.port_in_use`) so an orphan instance (e.g. pre-supervisor aisland) yields an actionable error instead of a crash-loop; (5) `project update` is a no-op on a byte-identical config, so a re-start after a failed run must `process start` explicitly (BaseService.start handles this); (6) NEVER write a secret literal into the document — credential env entries are `${VAR}` REFERENCES to workspace `.env` keys (e.g. Label Studio's `LABEL_STUDIO_PASSWORD=${LABELSTUDIO_PASSWORD}`), and `apply()` layers `supervisor.read_workspace_env()` over `os.environ` for the `project update` call because expansion is CLIENT-side at config load (the server loads `.env` once at startup and never re-reads it; an apply without the layering expands refs to empty strings and wipes the stored values — and a literal `$` in any document value would be expanded too, so don't put one in). The process-compose CLI surface these rules encode was verified empirically against v1.116.0.
- **macOS TCC Responsibility Lands On The Supervisor Binary (2026-07-09):** macOS attributes every supervised service's file access to the daemon tree's ROOT process — the process-compose server — NOT to the java/python actually doing the read. External-volume data (`DATA_ROOT=/Volumes/...`) therefore requires a Full Disk Access grant for the RESOLVED process-compose binary (System Settings → Privacy & Security → Full Disk Access), followed by a FULL supervisor restart (`aisland supervisor down && aisland start --background`) — granting java/python, or restarting only Jenkins, does NOT help. The denial surfaces as `PermissionError: [Errno 1] Operation not permitted` deep inside the service (canonical: huggingface_hub cache reads during a Jenkins notebook build) while the SAME command works interactively; the live-kernel-log signature is `kernel (Sandbox) System Policy: Python(NNN) deny(1) file-read-data /Volumes/...`. The grant pins to the VERSIONED Cellar path, so a process-compose upgrade silently orphans it — the formula is `brew pin`ned, and `supervisor._preflight_full_disk_access` warns at server start with the exact path to grant (skipping silently when the TCC db itself is unreadable — an inconclusive probe must never cry wolf). NEVER "fix" this class of failure by moving `DATA_ROOT` to the boot disk, editing project Jenkinsfiles, or weakening the volume's ownership settings; diagnose with a live `log stream` capture, not post-hoc file inspection (the file always looks fine afterwards). See README § "macOS: Full Disk Access for the supervisor".
- **A Container Bind Mount Sees ONLY What The Colima VM Shares, And `aisland docker start --mount` Is The One Place That Is Handled (`services/docker.py`, 2026-08-17):** `docker run -v <host>:<target>` binds a path INSIDE the VM, and colima (0.10.3, measured) shares ONLY `$HOME` by default — `colima ssh -- mount | grep virtiofs` → `/Users/<me>` and nothing else — so a bind mount from `$DATA_ROOT=/Volumes/…` mounts an EMPTY directory Docker creates inside the VM, with no error anywhere (an IQEngine container over `/Volumes/Store/RFUAV Annotations/2.0` listed 0 of the 77 sidecars; `docker exec … ls` → empty). Two more measured facts shape the flag: (1) passing ANY `--mount` to colima REPLACES the default rather than adding — `colima start --mount /Volumes/Store:r` left the VM with `/Volumes/Store` and NO `$HOME`, breaking every bind mount under `aisland/data/…` — so `_start_argv` always re-states `$HOME:w` ahead of the requested mounts (a user who names `$HOME` themselves keeps their choice); (2) colima PERSISTS the flags into `~/.colima/default/colima.yaml` (`--save-config` defaults true), so a later bare `aisland docker start` keeps the mounts, and that file is what `configured_mounts()` reads as "what the VM shares" (an empty `mounts:` list IS the `$HOME:w` default). Mounts apply at VM boot, so a mount missing from a RUNNING engine is REFUSED with `aisland docker restart --mount …` in the message — never restarted for the user, because a VM restart stops every container. **`is_running()` judges by `colima status`'s EXIT CODE, never its text** (fixed the same day): colima writes every status line to STDERR as `level=info msg="colima is running …"` and never prints `status: running`, so the old stdout grep was ALWAYS False — `launch()` then ran `colima start` against a live VM and, with `--mount`, colima still SAVED the ignored flags into the profile, leaving it claiming a share the VM did not have (reproduced on this machine before the fix). `parse_mount` RESOLVES symlinks because the VM resolves a shared symlink against its OWN tree (`colima ssh -- readlink ~/data` → `/Volumes/Store/`, which is only useful once `/Volumes/Store` is itself shared) and REFUSES a missing directory (colima would happily create and share an empty one). Pins: `tests/test_docker_service.py`.
- **Cross-Platform:** Process management MUST work on macOS, Linux, and Windows — via the supervisor: unix socket in `aisland/data/` on Unix, TCP (`AISLAND_SUPERVISOR_PORT`, default 9089) on Windows. The binary provisions via Homebrew (`f1bonacc1/tap/process-compose`, macOS) or the `USERSPACE_TOOLS` registry (Linux, arch-aware flat tarball).
- **Userspace Downloads Are Checksum-Verified:** Every `USERSPACE_TOOLS` entry MUST pin a per-architecture `sha256` (keyed by the same `{arch}` token used in the URL) taken from the upstream SHASUMS/checksums file. `_install_userspace_tool` verifies the tarball — freshly downloaded OR reused from cache — against the pinned digest BEFORE extraction; a mismatch aborts and deletes the tarball. When you bump a tool's `version`, refresh its digests in the SAME edit (`curl -sL <checksums-url>`), or the install will abort. An entry with no digest for the current arch installs UNVERIFIED with a loud warning — acceptable only as a transient state while pinning a brand-new tool, never for a shipped entry.
- **Recurring Venv Skew Becomes A Doctor Check, Not Just A Note (`aisland/doctor.py`, 2026-07-27):** When an environment-level breakage recurs — a shared-`.venv` package pair that goes inconsistent and fails FAR from its cause — documenting it in `AGENTS.md` is necessary but not sufficient: add a `check_*` function to `aisland/doctor.py` and register it in `CHECKS` so `aisland doctor` detects it in one line instead of a twenty-minute forensic session. Rules: (1) a check is cheap, read-only and SPECIFIC — it names a known skew and carries a copy-pasteable `remedy`, never a vague "something looks off" (`tests/test_doctor.py` asserts every failing result has a remedy); (2) any probe that IMPORTS a suspect library runs out-of-process via `_import_probe` — a broken native bundle can abort the interpreter, and a doctor that dies while diagnosing is worse than none; (3) `run_doctor()` returns an exit code (0 clean / 1 any failure) so a CI step can gate on it; (4) a check encodes an invariant enforced elsewhere and must cite WHERE — the opencv check mirrors `manager._ROOT_UV_BASE`'s `opencv-python ; sys_platform == 'never'` override (both distributions own `cv2/cv2.abi3.so` + `cv2/.dylibs/*`, so exactly one variant may be installed), and drifting from that source of truth is the failure mode to avoid. Do NOT turn the doctor into a generic linter of the venv; `pip check` already reports nominal-but-unsatisfiable pins (e.g. roboflow's opencv pin) that are NOT breakage.
- **`aisland clean` MOVES, Never Deletes — And Cleans ONE Project (`aisland/clean.py`, 2026-08-04):** the command that reclaims a checkout's git-ignored disk (`.venv/`, `build/`, caches, `lightning_logs/`, checkpoints) renames every ignored path into `aisland/data/backups/<project>/<YYYYMMDD-HHMMSS>/files/` — preserving its path relative to the project — and writes a `manifest.json` beside it; the space is genuinely reclaimed by the RETENTION SWEEP that every invocation runs (`--keep-days`, default 7, across ALL projects, BEFORE the move, so a run on a full disk frees the expiring space first). Do NOT "simplify" this to `git clean -Xdf`: in this workspace an ignored path can be load-bearing (a provisioned `bin/`, a service's `data/`, an `.env`), and the mistake is only ever discovered afterwards — a rename inside one filesystem costs the same as the delete would, so irreversibility buys nothing. Five properties are load-bearing, each protecting against a failure that is silent or unrecoverable: (1) **ONE project per invocation — never add `--all`**, whose blast radius is the shared `.venv` + every service's data dir + the workspace `.env` from a command whose name sounds routine; (2) **the workspace ROOT repo is refused BY NAME as well as by path** (`project_path` never returns the root for a plain name, so `aisland clean acme` would otherwise fall through to a generic "unknown project" and read as a typo); (3) **the project directory must BE its repository's root** — every project is a submodule (a `.git` FILE, not a directory) and `git status` run merely *inside* a repo reports THAT repo's ignored set, so a name resolving to a plain subdirectory would quietly clean the enclosing tree; (4) **an ignored entry that CONTAINS the backup store is split into its children** (`_split_around`) — this is not hypothetical, it is `aisland clean aisland`: its `.gitignore` ignores `data/` wholesale and the store lives at `data/backups`, so the single collapsed entry git reports contains the destination and moving it would swallow every previous backup; (5) **the sweep deletes ONLY directories whose name parses as `STAMP_FORMAT`** — the name, not an mtime (which any write underneath changes) and not the manifest (which an interrupted run never wrote) — so anything else a human left under the backup root survives. **The store has its own command group — `aisland backups list|restore` (2026-08-04):** `clean` acts on a project's WORKING TREE, `backups` acts on the STORE, which is why they are siblings rather than `aisland clean restore` (and it keeps the destructive verb one word long, so it is never typed by accident). **Restore MOVES too**, for the same reason the clean does — the disk was full enough to warrant a clean, so a second copy of the payload is the one thing that may not fit — and it CONSUMES the backup: `_forget_restored` rewrites the manifest to drop what left and deletes a backup whose payload is now empty, because a store advertising content it no longer holds makes the next `list` lie and the next restore fail halfway. Three rules: (1) **a path the project has a DIFFERENT copy of is SKIPPED, never clobbered** (the common case is a cache or `.venv` that rebuilt itself since the clean, and it is almost always the one to keep) and the skipped entries stay in the backup with **exit 1**, so a partial restore is visible to a script; `--force` replaces them and asks first — while a path the project has an **IDENTICAL** copy of is not a collision at all: it is reported `already`, the backup's redundant copy is DROPPED (keeping it would make the next `list` count it as recoverable content and make every later restore redo the comparison), and the exit code stays 0. **`_same_content` is a real comparison, not a heuristic, because it decides whether data may be deleted:** sizes + file counts first (a rebuilt `.venv` is rejected without reading a byte), then the path SETS, then byte-for-byte via `filecmp.cmp(shallow=False)`; an `OSError` anywhere means "not the same", so an unreadable file keeps the backup instead of silently dropping it. **NEVER swap this for the rsync-style size+mtime quick check** — the case it exists for is a path the operator already put back with `cp -R`, which restamps every file it writes, so mtime would call an identical tree different and leave the duplicate in the store until it expired (pinned by `test_a_hand_copied_tree_is_recognised_despite_new_mtimes`); (2) **the MANIFEST is the restore granularity, not the payload's top level** — it records the paths that actually MOVED, so a backed-up `data/jenkins` merges into a `data/` the project has since re-created, where a top-level walk would try to restore `data` itself and collide (a manifest-less backup — an interrupted clean — falls back to the payload's own top level, the same granularity `cp -R` uses); (3) **paths read from the manifest are VALIDATED, not trusted** (`_safe_rel` rejects absolute and `..`-containing entries) — it is a file on disk this code did not necessarily write. `clean` prints BOTH recovery forms on purpose: `aisland backups restore <project>` is the one to reach for, and the `cp -R` is the one that still works when this code is the thing that broke. **`aisland backups prune` is the retention sweep as a standalone verb** (the same `prune_backups` a clean runs, since a workspace nobody is cleaning would otherwise hold expired backups until the next clean of ANY project); it spans every project — the window belongs to the STORE, not to one project — and unlike the in-clean sweep it CONFIRMS first, because standalone it is the only thing happening and a mistyped `--keep-days 0` would empty the store outright, where inside a clean the sweep is bounded by the fresh backup taken right after it.
`git status --porcelain --ignored -z` is the discovery mechanism and its two flags are deliberate: `--ignored` COLLAPSES a fully-ignored directory to one entry (a 30k-file `.venv` is one rename, not 30k), and `-z` makes paths NUL-separated and never quoted, so a filename with a space or a newline round-trips. Sizes come from ONE `lstat` per entry that decides both size and shape (`_measure`) — the obvious `is_symlink() or not is_dir()` spelling stats twice AND lets `PermissionError` escape (`Path.is_symlink` swallows only ENOENT-ish errors), aborting the whole plan over one unreadable entry — and symlinks are measured, never followed, so a link into `$DATA_ROOT` counts as the one entry it is. Pins: `tests/test_clean.py` (a real git repo per test: collapse, the tracked-content-survives + restore round trip, the store surviving the project it lives in, every refusal, the sweep's name-only rule, and the CLI wiring).
- **Service Isolation:** Each service (Jenkins, MLflow) MUST have its own data directory and log file (`log_location` in the supervisor document). Never share state between services.
- **BaseService Contract:** All new services MUST extend `BaseService` and implement `start()`, `stop()`, `status()`, and `reset()`. Services own the domain logic (command line, env, readiness probe, config/.env publication); `BaseService` owns the supervisor delegation.
- **Job Seeding:** Jenkins `init` MUST auto-create multi-branch pipeline jobs for all workspace projects using config.xml templates.
- **Scaffolded Verify-Examples Runs Flat AND Directory Examples:** The Verify Examples step emitted by `aisland jenkins scaffold` (all three templates in `services/jenkins.py`: Jenkinsfile, Jenkinsfile.local, GH Actions ci.yml) executes `examples/*.py` AND `examples/*/run.py`. Directory examples opt into CI by shipping a `run.py`; network-dependent / install-only example apps (e.g. an installable demo CLI that needs a live API) opt out by not having one. Content pin: `tests/test_jenkins_scaffold.py::test_scaffold_emits_directory_example_runner`. Only confluid + liquifai were regenerated when this landed (2026-07-16); the sweep is now COMPLETE — all three files in all eighteen projects carry the loop, verified 2026-07-30 during a full `aisland jenkins scaffold --force`.
- **A Registered `slow` Pytest Marker SPLITS The Scaffolded Test Invocations (2026-08-09):** a project whose `pyproject.toml` registers a `slow` marker (`[tool.pytest.ini_options] markers = ["slow: …"]`) gets its generated CI test runs split by all three templates: the routine invocation deselects them (`pytest tests -m 'not slow' …`) and a separate leg runs `pytest tests -m slow` — a `Slow Tests` STAGE in both Jenkinsfiles, and a PARALLEL `slow-tests` JOB in `ci.yml` (`needs: [quality-gates]`, same as unit-tests, so it runs concurrently on its own runner and the routine result lands fast). The DECLARATION is the marker registration itself, never a new aisland knob — a project without the marker gets byte-identical output, so opting in cannot churn the other projects' committed CI files (verified by regenerating an unmarked project: zero diff attributable to this feature). **Exit code 5 is tolerated in the slow leg on both platforms** — a registered marker with nothing currently marked means "no tests matched", a valid state, not a failure. The trigger was a detection project's ~8-minute end-to-end smoke test (its Stream-mode dep-bump drift guard) sitting on every CPU-only push; the split moves it off the critical path while preserving the coverage per push. Pins: `tests/test_jenkins_scaffold.py::TestTheSlowMarkerSplitsTheTestInvocations` (the split in all three artifacts, the parallel-job dependency, the exit-5 tolerance, and the unmarked-project no-churn).
- **The Regenerate Header Must Be A RUNNABLE Command (2026-07-30):** all three templates emit `To regenerate: aisland jenkins scaffold <name> --force`. It said `--project <name>` for months, which fails with `Error: No such option: --project` — the project is a click ARGUMENT, not an option — so the only instruction a generated file carries was one that could not be followed (hit while regenerating recordstream after its framework declaration changed; the same wrong form had been copied into the workspace `AGENTS.md` provenance example, fixed with it). The pin PARSES the emitted line with the real `jenkins_scaffold` command object (`make_context`) instead of string-matching, so it tracks the CLI's signature rather than restating it, and it does reject the old form (`NoSuchOption`, checked). When a generator's CLI signature changes, its header changes in the SAME edit — then re-scaffold, because every previously-generated file still carries the old line. Pins: `tests/test_jenkins_scaffold.py::test_the_regenerate_header_is_a_command_the_cli_accepts`.
- **Shell Completion Has THREE Families, And The COMMAND Owns Them — `aisland completion install` (2026-07-31, supersedes "Keep All Three In `setup.sh` §5"):** The workspace has three kinds of CLI and each needs its own mechanism, all written into the ONE generated `.project.bashrc.completion`: (a) **liquifai apps** (the `liquifai.apps` entry-point group — `recordstream`, `sonair`, `annotaide`, `raidar`, …) via `liquifai.completion.install_for_apps`, called IN-PROCESS rather than through the `liquifai-install-completions` console script, so a PATH miss cannot silently skip the whole family; (b) **click apps** (`aisland` itself) via click's `_<PROG>_COMPLETE=<shell>_source` protocol, guarded on `BASH_VERSINFO >= 4.4` for bash because click REFUSES to emit for older bash and macOS `/bin/bash` is 3.2; (c) **argparse apps** (`streamstudio`) via `argcomplete` (`register-python-argcomplete`), which requires the app to call `argcomplete.autocomplete(parser)` before `parse_args` AND to DECLARE `argcomplete` as its own dependency (never lean on the transitive copy that arrives via fiftyone). A new CLI that is none of these three silently gets NO completion — that was the `aisland`/`streamstudio` gap. **The ~70 lines of inline shell in `setup.sh` §5/5a/5b were REPLACED by `aisland/aisland/completion.py` + `aisland completion install` (setup.sh now calls it in one line, pinned by `tests/test_completion.py::test_setup_sh_delegates_instead_of_reimplementing`).** The reason is a measured failure, not tidiness: a completion fix could only reach a machine via a FULL provisioning run (venv + `aisland setup` + git config), which nobody does to refresh a tab-completion — so this workspace's own generated file sat at its 2026-07-02 content while §5b, added 2026-07-27, never ran, and `aisland <TAB>` did nothing for a month with no signal anywhere. Do NOT move this logic back into shell or duplicate it there. **`--target-rc` is part of the contract:** the default is the workspace fragment `project.bashrc` sources, and a user may point it at `~/.bashrc` / `project.bashrc` instead; an existing rc is APPENDED to (marked blocks only), never overwritten. **Pruning is mandatory, not optional:** `liquifai/completion/install.py::_replace_block` MERGES by marker and leaves blocks it did not write untouched, so a renamed/removed CLI keeps a dead block forever (the `fluxstudio` -> `streamstudio` rename left exactly that; `matrainer` was pruned on the first real run, its CLI having been retired). Two safety rails, both load-bearing: the pruner STANDS DOWN when discovery found no liquifai app at all (that means discovery is broken, not that every app was uninstalled — pruning on that signal empties the file), and program lookup is VENV-FIRST (`sys.prefix/bin`, then `PATH`) so running from an unactivated venv cannot make every app look missing. Rationale: `docs/architecture.md`. Pins: `tests/test_completion.py`.
- **The Workspace Pins A Python VERSION, With An Upper Bound (`setup.sh` `WORKSPACE_PYTHON`, 2026-07-31):** the venv is built on the version `WORKSPACE_PYTHON` names (currently **3.13**), and an EXISTING venv is compared against it EXACTLY — not against a `>=3.12` range — because the pin has a ceiling as well as a floor, so a NEWER interpreter is just as wrong as an older one and a range check would silently keep it. The ceiling is about WHEELS, not language features: **TensorFlow 2.21 publishes cp310-cp313 only**, so on a 3.14 venv `uv pip install tensorflow` fails outright (*"we only found wheels ... cp310, cp311, cp312, cp313"*) and the framework is uninstallable no matter what `config.toml`'s `frameworks` selects — which is exactly how a workspace ends up believing a framework was omitted for size. Raise the pin only when every framework this workspace installs ships wheels for the next version; check TensorFlow first, it lags most. **A missing interpreter is provisioned by uv, never Homebrew (2026-08-17):** the fallback used to be `brew install python@X`, which is macOS-only and left every Linux/WSL machine dead at step 1 (`Homebrew is not installed`, Ubuntu 24.04 whose apt has no python3.13); it now runs `uv python install $WORKSPACE_PYTHON` + `uv python find` on every platform, installing uv into `~/.local/bin` first when absent. Homebrew's real job — the `[tool.aisland.sys-dependencies] brew` list (openjdk, process-compose, …) installed by `aisland setup` from inside the venv — is untouched; only Python moved. Pins: `tests/test_setup_sh.py` (runs the marker-delimited block in a real bash against stub `uv`/`curl`/`python3.13`: present interpreter → nothing installed; missing → uv provisions; missing uv → installer runs first; no `brew` on any code line). **`sh setup.sh` re-execs under bash (2026-08-17):** the script is bash (`[[ ]]`, `source`, `&>`) and under dash it half-ran — `&>` forked a background job, the rest printed `not found` — so a POSIX guard at the very top (`[ -z "$BASH_VERSION" ] && exec bash "$0" "$@"`) hands the invocation to bash; nothing but POSIX syntax may sit above that guard. Pin: `tests/test_setup_sh.py::test_running_under_sh_re_execs_under_bash`. Two further fixes landed with it, both real breakages hit while migrating: **`uv venv` does NOT seed pip** (unlike `python -m venv`), so the bootstrap died at `pip: command not found` and now seeds via `ensurepip`; and **`setup.sh` must call `aisland setup -y`**, because the bare form is INTERACTIVE and re-asks about every optional submodule — with no TTY (a background shell, CI, an agent) it blocks forever on `Activate 'raidar-ultralytics'? [y/N]:`. `-y` reuses the decisions already in `.git/config`; a genuinely NEW optional module still prompts, which is the deliberate conscious-opt-in behaviour. **One trap to know before running `aisland setup` on a machine mid-feature:** it runs `source apply`, which enforces the committed `[sources.*]` ref — so a project whose checkout you have moved to `dev/main` for unmerged work gets switched back to `main`. That broke sonair outright during this migration (confluid's `framework=` axis and its 0.3.0 version live only on `dev/main`; on `main` it is 0.2.0 without the axis, so every `@configurable(framework=...)` raises `TypeError` and sonair will not even install). Nothing is lost — `git switch dev/main` restores it — but the editable METADATA must be refreshed too (`uv pip install -e ./confluid`), since a branch switch changes the source while the recorded version stays stale and the resolver keeps failing the floor.
- **Generated Workspace Files Are Portable + Gitignored:** Files `aisland setup` writes to the workspace root (`pyrightconfig.json` via `manager._write_pyrightconfig`, the `project.bashrc` symlink, `.project.bashrc.completion`, `.gemini/settings.json` via `manager._write_gemini_settings`, and the root `uv.toml` via `manager._write_root_uv_toml`) are generated artifacts: gitignore them and regenerate on every setup (the workspace `config.toml` is the OPPOSITE — committed, hand-editable, never regenerated wholesale by setup; see the one-config-file mandate) so the tree never goes dirty and the output always tracks the live project set (discovered via `get_install_order` / `discover_projects` / `_discover_mcp_servers`, not a hand-maintained list). Prefer workspace-relative paths (e.g. pyrightconfig's `venvPath: "."`) — never bake in an absolute like `/Users/<name>/acme`. **Per-project editor config is generated too:** `_write_pyrightconfig` also drops a `pyrightconfig.json` into EVERY discovered project dir (`venvPath` walking back to the shared workspace `.venv`, sibling projects on `extraPaths` — for opening one project as its own editor root) and appends `/pyrightconfig.json` to that project's `.gitignore` when missing (`_ensure_gitignore_line`, append-only/idempotent like `_sync_mypy_path`). NEVER commit editor extraPaths again — the retired committed `.vscode/settings.json` copies drifted (they still named pre-rename projects) and leaked workspace sibling paths to external consumers; pyright ignores `python.analysis.extraPaths` from `settings.json` whenever a `pyrightconfig.json` is present, so stale local settings are neutralized. **Exception:** `.gemini/settings.json` MUST use ABSOLUTE venv paths because the MCP client (Gemini CLI) launches each server as a subprocess from an arbitrary cwd; that machine-specific absolute is precisely why the file is gitignored + regenerated per machine rather than committed. Don't "portability-fix" it to relative paths — that breaks the launcher.
- **Root `mypy.ini` Is Committed — Setup Only Appends To `mypy_path`:** Unlike the generated files above, the workspace-root `mypy.ini` is committed, hand-maintained policy (the per-module `[mypy-*]` sections). `aisland setup` (`manager._sync_mypy_path`) keeps exactly one line complete: `mypy_path` gains any discovered project that is missing, APPEND-ONLY — never remove entries (inactive submodules stay listed; mypy ignores path entries that don't exist on this machine, which keeps the committed file identical across machines) and never touch hand-added nested entries (`confluid/confluid`, `aisland/aisland`). Do not convert mypy.ini into a generated artifact — gates (Jenkins, fresh clones) must be able to run mypy before any setup has executed.
- **Root `uv.toml` Is Generated From The Activated Set (Never Committed With A Private Index):** The root `uv.toml` is built by `manager._write_root_uv_toml` = a workspace base (`_ROOT_UV_BASE` — the `override-dependencies` policy: the unified `lightning` and the GUI `opencv-python` dropped workspace-wide via uv's never-true `sys_platform == 'never'` marker, plus `opencv-python-headless>=4.12,<5`; rationale in the `_ROOT_UV_BASE` comment and the root `AGENTS.md`, pinned by `tests/test_uv_activation.py::_OVERRIDE`) **merged** with each ACTIVATED project's own `uv.toml` (union list keys like `extra-index-url` with dedup, last-wins scalars; hand-emitted via `_emit_uv_toml` with an AUTO-GENERATED provenance header). A private index (Company Artifactory) lives in the owning project's `uv.toml` (e.g. `vendorcli/uv.toml`) and reaches the root file ONLY when that project is activated. This is why the root `uv.toml` MUST stay gitignored and regenerated per machine: a non-corporate machine that does not activate vendorcli/bridge never gets the (unreachable) index, so `uv pip install` from the root never tries to contact it. NEVER commit a root `uv.toml` carrying a private `extra-index-url`, and NEVER move a private index back into the root base — it belongs in the project's `uv.toml`.
- **The Committed Workspace Configuration Is ONE File — `config.toml`, And `uv.toml` Is NOT Part Of It (`aisland/config.py`, 2026-08-01):** `sources.toml`, `frameworks.toml` and `trackers.toml` were folded into a single tracked `<workspace>/config.toml` — a top-level `frameworks` / `trackers` key plus one `[sources.<project>]` table each. They are the same KIND of thing (a committed shared decision whose per-machine deviation lives in `.git/config` and may never reach a tracked file), which is why `selection.py` was already a generalisation of `sources.py`; three headers and three readers for one concept was the duplication. **`config.py` owns the FILE and none of the DATA** — `selection.py` / `sources.py` hand it plain TOML values via `config.update(root, key, value)` — so it imports nothing from aisland and cannot join an import cycle; do NOT teach it about `Axis` or `ProjectSource`. Four properties are load-bearing: (1) **every write is whole-file but keyed**, so `aisland tracker set` re-renders without disturbing `[sources.*]` — the accepted cost, stated in the file's own header, is that a hand-edited file is normalised and its comments dropped by the next command that writes; (2) **scalars are emitted before tables**, because TOML binds a bare key to the most recent table header and `frameworks = [...]` written after `[sources.confluid]` silently becomes `sources.confluid.frameworks` (pinned by `tests/test_config.py::test_scalars_are_emitted_before_tables`); (3) **an absent KEY is what *unset* means** — it used to be an absent FILE, which three concerns can no longer share — while an empty document still deletes the file so a workspace configuring nothing carries no stub; (4) **the legacy files are still READ** per key and deleted by the first write (or `aisland config migrate`, which `aisland setup` calls), because without the fallback a pre-merge checkout reads as "nothing is configured", which for sources means every project silently unmanaged. **`uv.toml` stays separate and always will:** uv reads only its own settings file and REJECTS a foreign table — measured against uv 0.11.8, `UV_CONFIG_FILE=config.toml uv pip install …` fails with ``The `sources` field is not allowed in a `uv.toml` file`` — and it is generated per machine + gitignored (a private index reaches it only when its project is activated), so it is not the same kind of artifact. Never move `manager._ROOT_UV_BASE` into `config.toml`, and never re-split `config.toml` back into per-concern files. Rationale: `docs/architecture.md`. Pins: `tests/test_config.py` (section isolation, the scalars/tables order, unset-vs-empty, the migration, and that every `aisland …` command the file's comments name resolves against the REAL click tree).
- **Project Sources Are Two-Layered, And Only The COMMITTED Layer May Reach A Committed File (`aisland/sources.py`, 2026-07-28):** `aisland source` decides where each workspace project's package comes from — THREE kinds (`SourceKind`, 2026-07-28): `local` (checked out on a `ref`, installed editable **with the SAME target `aisland setup` computes** — `selection.editable_target`: the `dev` extra plus every selected framework/tracker extra; until 2026-08-22 the source path installed the bare directory, so `aisland source set confluid local` silently dropped `[dev]` from the venv and a framework project lost its selected backends — pinned by `tests/test_sources.py::TestApplySource::test_local_installs_the_dev_extra_and_the_selected_frameworks`), `github` (submodule deinit'd, directory EMPTY, installed from the remote at `ref`) and `pypi` (deinit'd, published wheel). `local`/`github` both carry a `ref` (`REF_KINDS`) and differ ONLY in whether a working tree survives; `github`/`pypi` both empty the directory (`DETACHED_KINDS`, exposed as `ProjectSource.detached` — derive from these tuples, never re-test kinds by hand). The naming is deliberate and must not be "simplified" back to `git`/`github`: the two commands are one word apart and two of the three run `git submodule deinit`, so a three-character difference between keeping and DELETING a checkout was rejected. A project with no entry is *unmanaged* and keeps the historical behaviour exactly — `DEFAULT_REF = "main"` exists so an unmanaged project and an explicit `local:main` produce byte-identical build files. Configuration is layered like submodule activation: the COMMITTED `[sources.<project>]` tables of `<workspace>/config.toml` (shared, see the one-config-file mandate) plus a per-machine `git config --local aisland.source.<project>` override (never committed). **The split of what each layer drives is the invariant, not a detail:** the committed layer alone drives the `*.code-workspace` `folders` list (via `sources.sync_code_workspace`) and the ONE bit the runner-side CI files read; the EFFECTIVE source (override, else committed) drives only the submodule checkout and the shared `.venv`. NEVER let an override reach a tracked artifact, and NEVER read the effective source inside the scaffolder. **CI reads the published/not bit and NOTHING else — in particular it IGNORES the `ref` (2026-07-28):** a runner always clones `DEFAULT_REF`, and a `pypi`-sourced dep is dropped from the pre-install loop so `.[dev]` resolves it from the index. A `ref` is a DEVELOPMENT pin; letting it reach a tracked file would publish one developer's choice to every consumer's CI *and* rewrite seventeen projects' committed files on every switch. `_publishedness_changed` enforces the corollary: `aisland source set --ref`, and any `local` <-> `github` switch, regenerate NOTHING; only crossing the `pypi` boundary re-scaffolds. **`Jenkinsfile.local` reads NO source configuration at all** — every internal dep gets the IDENTICAL `[ -f "$WORKSPACE_ROOT/<dep>/pyproject.toml" ]` guard falling back to `git@main`, making that file a function of the dependency LIST alone, which no `aisland source` change of any kind can rewrite. The guard is not defensive polish: it asks at BUILD time exactly the question the config answers ("does this machine have a checkout?"), which is also what makes a per-machine override — by design invisible to tracked files — work instead of failing on an empty directory. Do NOT reintroduce per-kind branching there; the uniformity IS the property. **The predicate MUST test the FILE, never `-d` on the directory (2026-07-29):** `git submodule deinit` empties the working tree but LEAVES THE DIRECTORY, so `[ -d ]` is true for every detached dep — the editable branch then fires against an empty directory and every consumer's local pipeline dies at the Initialize stage with ``error: <dir> does not appear to be a Python project, as neither `pyproject.toml` nor `setup.py` are present``, with the git fallback unreachable. `pyproject.toml` is the file `uv pip install -e` actually consumes, so testing it asks the real question. Pinned by `tests/test_sources.py::TestScaffoldHonoursSources::test_guard_takes_the_git_branch_on_a_deinitd_directory`, which runs the emitted shell against a real empty dir rather than asserting on the emitted string. Its one accepted cost: a `pypi`-sourced dep is built from `main` in the local pipeline rather than from the released wheel, so that file alone diverges from the venv and from `ci.yml` — deliberate, because the local pipeline exists to catch breakage BEFORE a release. Availability on PyPI is decided ONCE, at `aisland source set … pypi` time (the provenance probe); scaffolding MUST NOT re-probe the index, or committed file content would depend on network reachability and an offline scaffold would flip every project to git URLs. Three more rules the implementation encodes, each protecting against a failure that would otherwise land AFTER the directory was already emptied: (1) a `pypi` switch resolves the distribution name from `pyproject.toml` BEFORE deinit (afterwards there is nothing left to read — which is why `distribution` is persisted into the registry); (2) each detaching kind is validated BEFORE the deinit and an inconclusive probe NEVER rejects — `_pypi_provenance` requires the published metadata to point at `github.com/Gearlux/…`, NOT merely that the name resolves (PyPI names are global, so a bare existence check would install a stranger's package into the shared venv when a workspace name is taken — `purifai` is exactly such a name), and `_remote_ref_exists` requires the `github` ref to resolve via one `git ls-remote` (non-zero exit = unreachable = inconclusive; exit 0 with empty output = the remote answered and has no such ref); an unreachable index or remote warns and continues, never a false rejection that would block an offline machine; (3) neither `git switch` nor `git submodule deinit` is ever forced — a dirty submodule refuses, is reported **with the remedy matching the ACTUAL blocker** (`_deinit_remedy`, 2026-07-28: git words BOTH refusal causes as "contains local modifications", but their fixes live in different repositories — a dirty work tree is fixed IN the submodule, while a **stale gitlink** (the checkout sitting at a commit other than the one the superproject records, the common case right after committing in a submodule without bumping the pointer) is fixed by committing the pointer in the WORKSPACE repo; the message probed nothing and always said "commit or stash the changes in `<sub>`", sending the operator hunting through a spotless tree — so probe each, report only what is true, and stay generic when a probe cannot answer), the venv is left untouched, AND `set_project_source` ROLLS THE CONFIGURATION BACK, because a registry claiming a state the working tree does not have would be re-attempted by every subsequent `aisland setup`. `manager.reconcile_submodules` folds `sources.detached_projects()` into its active set so the activation machinery cannot re-init a directory the source says is empty. **A DETACHED project must still be discoverable by the scaffolder:** `jenkins.discover_gearlux_projects` reads each submodule's `pyproject.toml` for its distribution name, which an emptied directory no longer has — so it ALSO seeds from the committed registry's `distribution` field (that field exists for exactly this reason). Dropping that fallback is silent and severe for `github`: the dep vanishes from the internal set, the git-URL pin disappears, and CI resolves the PyPI RELEASE instead of the requested ref (or fails outright for an unpublished project) — found by running a real scaffold, not by a unit test, and now pinned by `tests/test_sources.py::TestScaffoldHonoursSources::test_github_dep_survives_its_own_empty_directory`. The `github` remote URL comes from `.gitmodules` (`sources.remote_url`), never a hardcoded `github.com/Gearlux/<name>`, so the non-GitHub submodules work too; `pip_vcs_url` rewrites an scp-style `git@host:org/repo` to `git+ssh://git@host/org/repo` because pip cannot parse the scp form. Pins: `tests/test_sources.py` (layering, the byte-lossless `folders` round trip, the guard's emission AND its behaviour on a real empty directory, the argv sequence per kind, the reconcile interaction).
- **Selection Is Axis-Generic — `aisland/selection.py` Owns The Mechanism, `frameworks.py` Is A FACADE (2026-08-01):** the declare/select machinery moved to `aisland/selection.py` and is parameterized by an `Axis` (`name`/`plural` -> the `<plural>` key of the workspace `config.toml`, the `aisland.<plural>` git key, and the `[tool.aisland] <plural>` declaration table). TWO axes exist and are **SIBLINGS, never merged**: `FRAMEWORKS` (what a machine TRAINS WITH) and `TRACKERS` (where results GO — `matrainer[mlflow]`/`[aim]`/`[tensorboard]`/`[wandb]`). Folding the backends into `frameworks` would install a tracking client because someone picked a training engine; that is why matrainer's `pyproject.toml` declares them as a separate `trackers = [...]` key, and why `aisland tracker` is its own command group rather than more names under `framework`. **`aisland/frameworks.py` is now a thin facade** keeping every `*_frameworks` name bound to the framework axis, so `manager.py`, `services/jenkins.py`, `cli.py` and `tests/test_frameworks.py` were untouched by the move — do NOT "clean it up" by rewriting those call sites; the facade is what made a 200-line mechanism shareable without a ripple. A module named `frameworks` owning the tracker axis would describe its first consumer rather than its role (the same correction as matrainer's `lightning.metrics` -> `torch.metrics`). **Three rules the generic code encodes:** (1) `all_extras()` spans BOTH axes and is what `setup` and `apply_selection` install — a target naming only the axis being changed describes a package the operator never asked for, so changing trackers must not drop the framework extras; (2) the CI scaffolder loops `AXES` and reads `read_committed` ONLY, never `effective` — a per-machine override reaching a tracked build file is the failure the whole two-layer split exists to prevent, and for trackers it is worse than for frameworks because a runner that stops installing mlflow makes those tests **SKIP rather than fail** (`pytest.importorskip`), i.e. a green CI that checks nothing; (3) a project declaring neither axis emits the historical `.[dev]` unchanged. Pins: `tests/test_selection.py` (axis independence, `all_extras` across both, the header naming the right command), `tests/test_frameworks.py::TestScaffolderUsesThisModule` (the committed-only binding + that the scaffolder covers every axis).

- **`aisland clearml` VENDORS NOTHING — Pinned Upstream Compose + A GENERATED Override (`services/clearml.py`, 2026-08-01):** the ClearML server is seven containers, and upstream publishes the compose that wires them; this service fetches that file at a **release tag** (`CLEARML_SERVER_VERSION`, currently `v2.4.0`) and verifies it against `COMPOSE_SHA256` before caching — the `USERSPACE_TOOLS` checksum rule applied to a config artifact, and the reason the pin must be a TAG and never `master` (a digest pinned to a moving ref breaks on upstream's next commit; `tests/test_clearml_service.py` asserts it). **Upstream hardcodes `/opt/clearml/...` host paths**, which would put service state outside the workspace and need root — so aisland layers an override that remaps every bind mount into `aisland/data/clearml/state`. Three facts hold it together, all MEASURED rather than assumed: (1) **compose merges a service's `volumes` by container TARGET** — an override naming the same target REPLACES the entry rather than adding a second (verified with `docker compose config` before any of this was written; had it appended, the whole design was wrong); (2) the override is **GENERATED from the upstream file**, never hand-listed, so bumping the version cannot leave a stale path behind and a mount upstream adds later is remapped automatically; (3) upstream comes FIRST in the `-f` order, because compose applies later files over earlier ones. **Docker owns the lifecycle, not the supervisor** — `launch`/`stop`/`status` shell out to `docker compose`, and `info()` deliberately does NOT call `super().info()` because the base prints a "Supervisor: process-compose" line that would send an operator to the wrong tool. **Verified end to end 2026-08-01:** all eight containers up, web `HTTP 200`, `auth.login`… no — `debug.ping` returned `result_code: 200`, 209 MB of state under `aisland/data/clearml/state` and **`/opt/clearml` absent from the host**, then `stop` removed the containers with the state intact. **Credentials are minted HEADLESSLY, and the mechanism is not the obvious one (2026-08-01):** a fresh stack reports `login.supported_modes` -> `basic.enabled: false`, so nothing can log in until a fixed user exists. Enabling one through `CLEARML__apiserver__auth__fixed_users__users__0__username=…` environment variables **does not work** — that override cannot express a LIST OF OBJECTS, and the server then dies on EVERY login with `FixedUser() argument after ** must be a mapping, not str` (measured; the stack looks healthy and only auth is broken). The working mechanism is ClearML's documented one: an `apiserver.conf` written into the mounted config directory (`state/config/`, which the override already binds to `/opt/clearml/config`), **before** `up`, because the apiserver reads that directory at startup. `launch()` then waits for `debug.ping`, calls `auth.login` + `auth.create_credentials`, and records `CLEARML_API_ACCESS_KEY`/`SECRET_KEY` in the workspace `.env`. The password IS a literal in that file — the server has to read it — so it is 0600 and lives in gitignored machine-local state beside the `.env` that already holds it; an existing login is REUSED rather than regenerated, since a fresh password would not match the server that already has the old one. Minting never raises: a stack that is otherwise up must not fail over a tracking convenience. **Verified end to end 2026-08-01:** a `ClearMLTracker` against the live server produced a `completed` task carrying the hyperparameters, the flattened `datasets` section, the manifest in the Configuration tab, and `manifest.yaml`/`manifest.json`/the log as artifacts. One interop constraint found while doing it: ClearML rejects a task name shorter than three characters (`Data validation error: name=String value is too short`).
- **`aisland iqengine` Is ONE Digest-Pinned Container Over A READ-ONLY Directory, And `start` Diagnoses The Two Silent-Empty Cases (`services/iqengine.py`, 2026-08-17):** the SigMF viewer is upstream's image run exactly as its docs say (`-v <dir>:/tmp/myrecordings`, `IQENGINE_BACKEND_LOCAL_FILEPATH=/tmp/myrecordings`, `IN_MEMORY_DB=1` — no Mongo, the index is rebuilt from the directory every start), nothing vendored, Docker owning the lifecycle (`docker run`/`rm -f` on the fixed name `aisland-iqengine`; `info()` does NOT call `super().info()`, same reason as ClearML). - **`aisland aim` Serves A REPOSITORY, And The Path Is The Contract (`services/aim.py`, 2026-08-01):** Aim has no server — `aim up --repo <dir>` serves a directory — so the service is only useful if it serves the SAME directory the tracker writes to. `launch()` therefore publishes the path to the workspace `.env` as **`AIM_REPO`** (`_publish_repo`, replacing a stale entry in place and leaving neighbouring keys untouched), and a run config points its tracker at `$AIM_REPO`. - **Framework Selection Is Two-Layered Like Sources; Only The COMMITTED Layer May Reach CI (`aisland/frameworks.py` -> now `aisland/selection.py`, 2026-07-30):** workspace packages keep their core framework-free and put each ML framework behind an EXTRA (`recordstream[torch]`, `sonair[lightning]`/`[keras]`), so something must decide WHICH — before this module `aisland setup` installed `<project>[dev]` and nothing else, which after the extras split produced a sonair with no backend at all. TWO halves, deliberately separate: a project **declares** which of ITS extras are frameworks in its own `pyproject.toml` (`[tool.aisland] frameworks = ["lightning", "keras"]`), and the workspace **selects** framework NAMES; each project installs what it declares ∩ what is selected (`extras_for`, ordered by the DECLARATION so the emitted target is stable however the names were typed). Declaration is required rather than guessed because extras are a mixed bag — `dev`/`http`/`viz`/`notebook`/`all` sit in the same table as `torch`/`keras`, and a name match would install a docs extra on a machine that asked for a training engine. **Declare only IMPLEMENTED frameworks:** sonair keeps `jax`/`mlx`/`huggingface` extras so its CLI templates can print a real install command, but declaring them would install three frameworks nothing can run. Declaring is the MENU, not the install: sonair added `tensorflow` and `fastai` to its declaration on 2026-07-30 when both backends became real, and the committed SELECTION still omits `tensorflow` — so nothing new installs until someone runs `aisland framework set … tensorflow`. That split is what lets a project advertise a working backend whose install cost (TensorFlow is a large download) stays a deliberate opt-in. It is NOT a dependency conflict — the long-standing "TF forces protobuf across mlflow/tensorboard/wandb" claim was measured wrong and corrected 2026-07-30; see sonair's `AGENTS.md`. A project declaring NONE is inert — it installs exactly as before, which is what keeps this change invisible for the fifteen-odd projects that ship no framework extra. The names line up across projects ON PURPOSE (`keras` is `keras` everywhere) so ONE selection drives everything with no per-project mapping table. **Layering mirrors `aisland/sources.py` exactly, and the same invariant is the point:** the COMMITTED `frameworks` key of `config.toml` is the shared default AND the only layer `jenkins.scaffold_pipelines` reads (via `ci_extras`), while the per-machine `git config --local aisland.frameworks` drives ONLY this machine's `.venv`. Never let an override reach a tracked build file — one developer narrowing to torch locally would silently stop every runner from testing the Keras backend, a failure that shows up as a green CI that no longer checks anything. **`None` (unset) is NOT `[]` (chose nothing):** setup PROMPTS for the former and honours the latter silently; `--non-interactive` with nothing recorded selects everything rather than hanging or producing a workspace that cannot train, and an explicit `--framework` flag is RECORDED so it is a one-time flag. **`apply_frameworks` MUST iterate `get_install_order`, never `discover_projects`** — a consumer's extra can name a sibling's (`sonair[keras]` requires `matrainer[keras]>=0.1.0`), so installing the consumer first resolves against the sibling's ALREADY-INSTALLED metadata and uv warns `does not have an extra named 'keras'` while quietly installing without it (observed on the first real run). Accepted cost: uv does not UNINSTALL a deselected extra — guessing which packages 'belonged' to one is unsound, so a stale wheel costs disk, not correctness; recreate the venv for a clean set. Verified 2026-07-30 that the full framework set co-resolves (torch 2.13 + tensorflow 2.20 + keras 3.15 + pytorch-lightning 2.6.5 on one numpy), so "CI installs everything" is a measured option rather than a hope. **ONLY projects that OFFER a choice are declarable, and the four that REQUIRE torch are deliberately NOT (decided 2026-07-30 by reading each, not by counting imports):** `signals` (`schema.py`, "THE builder for the record model", enforces `torch.complex64` IQ — torch IS the canonical representation), `deltaid` ("a standard PyTorch-Lightning semantic segmenter" per its own docstring), `raidar` + `raidar-ultralytics` (torch/ultralytics detection trainers whose `__init__.py` imports them eagerly). Moving their deps behind a `[torch]` extra was considered and REJECTED — `pip install raidar` would yield a package whose `__init__` raises `ImportError`, dishonest packaging for a project that genuinely needs torch. **Do NOT "finish the job" by declaring them**; the accepted consequence is that `aisland framework set keras` on a FULL workspace still installs torch, because this command narrows MULTI-BACKEND projects and never promised a framework-free venv. `torpaido` was NOT such a case and was fixed instead: it declared `torch` while referencing it zero times across its three modules, so the dependency was dropped outright. If a genuinely torch-free venv is ever wanted, the path is a new "skip this project unless its framework is selected" mechanism, not a fake extra. Rationale: `docs/architecture.md`. Pins: `tests/test_frameworks.py` (the layers, the unset/empty distinction, the setup precedence, and that the scaffolder reads the committed layer ONLY).
- **The `*.code-workspace` `folders` List Is Edited LINE-WISE, Never Reparsed (2026-07-28):** the workspace file is **JSONC** — `settings` carries `//` comments and trailing commas, so `json.load` fails on it outright (line 121 of the real `acme.code-workspace`). `sources.sync_code_workspace` therefore bracket-scans only the `folders` span and edits it as lines, and a disabled project is **commented out in place** rather than deleted. That is not cosmetic: it keeps the entry's position in a list that is dependency-ordered rather than alphabetical, and makes comment→uncomment byte-for-byte lossless, so flipping a project to `pypi` and back leaves `git diff` clean (asserted against the real file's structure in `tests/test_sources.py::TestSyncCodeWorkspace::test_round_trip_is_byte_identical`). NEVER "simplify" this to a JSON round trip — it would reformat a hand-maintained committed file and drop every comment in it. Entries for projects NOT named in `config.toml`'s `[sources]` (`vendorcli`, `signals-bridge`, `raidar-ultralytics`) are left untouched; they are governed by the activation mechanism, not this one.
- **Submodule Activation Is Per-Machine + Prompt-Driven:** `aisland setup` resolves *optional* submodules (`manager._project_is_optional` → ships its own `uv.toml` OR is `active = false` in `.gitmodules`; ordinary projects auto-activate and are never prompted) and records the answer per-machine in `.git/config` (`submodule.<name>.active`, via `_set_local_submodule_active`) — NEVER in committed `.gitmodules` (that file's `active` flag is the shared default only). Semantics (`_resolve_submodule_activation`): a decided module (a value already in `.git/config`) is honored silently; an undecided/NEW optional module is **prompted even under `--non-interactive/-y`** (a machine must consciously opt into a private/corporate project before it tries to use its index or clone its remote); `--activate <name>` / `--deactivate <name>` set the decision without prompting. `reconcile_submodules` then aligns the working tree with `committed_active if local is None else local`, so a per-machine deactivate deinits a committed-active submodule. Keep the deinit protective (no `-f`) unless the user asks otherwise.
- **An Internal Dependency Spec MUST Accept The Sibling's Declared Version (2026-08-25):** the workspace installs its own projects from local checkouts, so a specifier naming a sibling is only ever satisfied by the version that sibling's `pyproject.toml` declares. When the two drift nothing warns at edit time — the failure lands mid-`aisland setup`, as a uv refusal after an arbitrary prefix of `get_install_order` has already been installed, leaving the venv half-updated with stale editable metadata that still *imports* fine (so `python -c "import matrainer"` passes while `pip check` reports the contradiction). Two drifts wrote this rule: `recordstream` released as the pre-release `0.1.0a1`, and under PEP 440 a plain `>=0.1.0` EXCLUDES every pre-release of `0.1.0`, so 24 specs became unsatisfiable — the BASE deps had been migrated to `>=0.1.0a1` and the ones inside `optional-dependencies` were missed, which is why the check walks EXTRAS, not just `project.dependencies`; and `vendorcli` capped `liquifai>=0.1.0,<0.2` while `liquifai` moved to `0.2.0`, so installing vendorcli silently EVICTED the local editable checkout and put the last PyPI build that fit the cap in its place (`aisland source list` still said `local:dev/main` while `import liquifai` resolved into `site-packages`). Pinned by `tests/test_workspace_dependency_specs.py` — `find_unsatisfiable_specs(get_workspace_root())` must stay empty. Two deliberate carve-outs: a dependency written with NO specifier (a bare `"recordstream"`) makes no version claim and is not flagged, and a project whose `config.toml` source is `github`/`pypi` is deinit'd to an empty directory, declares no local version, and resolves against a real index instead. Bumping a project's own `version =` is therefore never a one-file change: every sibling spec naming it has to still accept it, extras included.
